# Research: Multiple Emails and Phones per Person

No NEEDS CLARIFICATION items remained after the 2026-08-07 clarification session — the stack is fully fixed by the existing codebase (TypeScript/Fastify/drizzle/SQLite/Vue, no new dependencies). Research therefore consolidates the design decisions that the spec leaves to engineering.

## D1 — Storage: two sibling child tables

**Decision**: Two new tables, `person_emails` and `person_phones`, each with `id` (autoincrement PK), `person_id` (FK → `people.id`, cascade delete), `value` (text, not null), `is_primary` (integer boolean, not null, default 0), `created_at`. The `people.email` and `people.phone` columns are dropped.

**Rationale**: The spec's Key Entities are exactly these two record types, and their uniqueness rules differ (case-insensitive vs exact), which maps cleanly to one expression index per table. Child rows with FKs give cascade delete for free (person deletion already cascades task links the same way) and let DB indexes enforce cross-person uniqueness, which no JSON-column design can.

**Alternatives considered**: A single `contact_entries` table with a `type` column — workable with partial indexes, but every query and index needs a `type` predicate and the two types never join, so two plain tables are simpler. A JSON array column on `people` — rejected because uniqueness across people (FR-007/FR-008, SC-004) cannot be enforced by the database and every check becomes a full scan in application code.

## D2 — Uniqueness: DB indexes as backstop, service pre-checks for messages

**Decision**: `person_emails` gets `uniqueIndex on lower(value)`; `person_phones` gets `uniqueIndex on value`. The service performs an explicit conflict query first (excluding the entry's own id on edits) and returns a typed conflict result that routes map to the exact messages; the index is the race/bug backstop, not the error path.

**Rationale**: This is the codebase's existing pattern — `people_email_unique` on `lower(email)` plus `emailConflictExists()` — extended to entries. SQLite `lower()` folds ASCII case only; that matches the current email-uniqueness behavior exactly, so nothing gets stricter or looser. Phones index the raw stored text, giving the spec's no-normalization semantics ("555-0100" and "5550100" coexist) with zero extra code.

**Alternatives considered**: Relying on the unique index alone and catching `SQLITE_CONSTRAINT` — rejected because typed service results ("email-conflict" vs "phone-conflict" vs "not-found") keep routes clean and match the existing service style. Normalizing phones before comparison — explicitly out of scope per spec.

## D3 — Exactly-one-primary invariant: `is_primary` flag + partial unique index + transactional service logic

**Decision**: Each table carries `is_primary` with a partial unique index on `(person_id)` `WHERE is_primary = 1`, so the DB guarantees *at most one* primary per person per type. The service guarantees *exactly one when any exist*: the first entry added to an empty list is stored primary; `markPrimary` clears the old flag and sets the new one in a transaction; `remove` promotes when it deletes the primary (D4). Marking the current primary again is a no-op; editing a value never touches the flag.

**Rationale**: A flag on the entry keeps the entry self-describing (the read model needs `isPrimary` per entry anyway for the UI) and the partial index makes the invariant impossible to violate silently. drizzle already uses expression/partial `uniqueIndex` in this schema, so this is proven ground.

**Alternatives considered**: A `primary_email_id`/`primary_phone_id` pointer on `people` — rejected: circular FK between `people` and the entry tables forces two-step inserts and nullable-pointer edge cases. An ordering column where position 0 is primary — rejected: conflates ordering with primacy and makes "mark primary" a reorder.

## D4 — Promotion rule: lowest surviving id

**Decision**: When the primary entry is removed and others remain, the surviving entry with the lowest `id` is promoted, inside the same transaction as the delete.

**Rationale**: Autoincrement ids are insertion-ordered, so lowest id *is* the spec's "earliest-added remaining entry" (Assumptions), and it is unambiguous even when `created_at` timestamps tie within a millisecond.

**Alternatives considered**: Lowest `created_at` — same intent but tie-prone; ids are strictly ordered.

## D5 — Migration: one file — create, carry over, drop

**Decision**: A single migration (0004) generated by `drizzle-kit generate` for the DDL (new tables + dropping `people.email`/`people.phone`), with hand-added carry-over statements inserted between table creation and column drop: `INSERT INTO person_emails (person_id, value, is_primary, created_at) SELECT id, email, 1, created_at FROM people WHERE email IS NOT NULL;` and the same for phones. Runs automatically at boot via the existing `migrate()` call.

**Rationale**: One file keeps carry-over and column drop atomic — no migration ordering to get wrong, no window where both representations exist. Existing rows' values become primary entries verbatim (FR-014); rows with NULL simply produce no entry (zero entries is valid). There is no production data (clarified 2026-08-07), so no conflict handling is needed; SC-002 is verified by the automated seeded-data test (D10).

**Alternatives considered**: Separate schema and data migrations — more moving parts for no benefit at this data scale. Keeping the old columns as denormalized primary caches — rejected: two sources of truth for FR-002's invariant.

## D6 — People search keeps its existing reach: name + primary email

**Decision**: `listPeople`'s substring search matches first name, last name, and the person's **primary** email (via a correlated subquery/join on `is_primary = 1`), exactly the reach it has today. The MCP `search-people` tool inherits this unchanged.

**Rationale**: The spec explicitly puts "searching/filtering people by any address or number" out of scope; today's search matches the single stored email, and the primary entry is that value's successor. Widening to all addresses is future ingestion-adjacent work.

**Alternatives considered**: Matching all addresses — deferred as out of scope. Dropping email from search — a silent regression, rejected.

## D7 — API shape: sub-resource routes; person payloads carry full entry arrays

**Decision**: Entry management is exposed as REST sub-resources — `POST /api/people/:personId/emails`, `PATCH .../emails/:entryId`, `PUT .../emails/:entryId/primary`, `DELETE .../emails/:entryId`, and the mirror set under `/phones` (8 endpoints). Every person payload (`GET /api/people`, `GET /api/people/:id`, and the mutation responses) now includes `emails` and `phones` arrays of `{ id, value, isPrimary, createdAt }` ordered by `id` ascending; the client derives primary for the list rows. Entry mutation endpoints return the person's full refreshed entry list of that type, so the UI re-renders from one response.

**Rationale**: Sub-resources map one-to-one onto the spec's four operations and give each failure a natural status (400 blank, 404 unknown person/entry, 409 duplicate) with the exact messages the spec requires. Full arrays on the person payload serve both the detail page and the list without a second endpoint, at single-user scale.

**Alternatives considered**: Whole-list PUT (client sends the complete desired array) — rejected: pushes invariant enforcement to the client and makes per-action validation messages ambiguous. Server-computed `primaryEmail`/`primaryPhone` convenience fields — redundant with the arrays; the MCP layer projects primaries where the flat shape is actually required (D9).

## D8 — Person input split: create keeps email/phone, update drops them

**Decision**: `personInputSchema` splits into `createPersonInputSchema` (names + optional single email/phone + extraFields — unchanged shape) and `updatePersonInputSchema` (names + extraFields only). `createPerson` inserts provided values as primary entries in the same transaction and now pre-checks phone uniqueness too, returning distinct `email-conflict`/`phone-conflict` results (409 with the matching message; no person row is created on conflict). `updatePerson` can no longer touch contact data (FR-015). `PersonForm` gains a mode so the edit page renders it without the email/phone inputs.

**Rationale**: FR-011 keeps the create form's single inputs; the 2026-08-07 clarifications require phone-duplicate rejection at create and removal of contact inputs from edit. Zod object schemas strip unknown keys, so stray `email` in an update body is ignored rather than erroring — matching "the form no longer has the field" semantics.

**Alternatives considered**: Rejecting update bodies containing email/phone with 400 — needless strictness for a single-client API. A separate create-vs-edit form component — the shared form with a visibility switch is smaller and keeps existing tests meaningful.

## D9 — MCP tools: shapes frozen, values become primary projections

**Decision**: No MCP tool is added, removed, or reshaped. `get-person` keeps `email`/`phone` nullable-string fields, `search-people` keeps `email`, `get-task`'s people keep `email` — each now populated with the person's primary entry value (null when the person has none of that type). The projection happens in the service read model so all consumers agree.

**Rationale**: FR-012 requires every single-value surface to present the primary; the spec puts tool changes beyond that out of scope (they belong to the `mcp-tool-expansion` feature). Freezing the schemas means zero churn for connected clients.

**Alternatives considered**: Adding `emails[]`/`phones[]` to tool outputs — out of scope here, noted for `docs/product/future/mcp-tool-expansion.md`.

## D10 — Migration carry-over test: replay raw SQL on a legacy-shaped DB

**Decision**: The SC-002 test builds an in-memory SQLite database by executing the raw `.sql` files of migrations 0000–0003 in order (splitting on drizzle's `--> statement-breakpoint` marker), seeds people rows with legacy single `email`/`phone` values (including NULLs and mixed case), then applies migration 0004 and asserts every seeded value reappears as exactly one primary entry on the right person with nothing lost or altered.

**Rationale**: This is the only way to genuinely test the carry-over: the drizzle `migrate()` helper always runs the full chain against the current schema, so the legacy state must be constructed by replaying the pre-feature migrations verbatim. Raw `better-sqlite3` + file reads keep the test dependency-free and honest — it exercises the very SQL that will run in production at boot.

**Alternatives considered**: Hand-building the legacy schema with `CREATE TABLE` statements in the test — drifts from the real migration chain and silently diverges. Testing against a checked-in fixture `.db` file — binary fixtures rot and hide their contents from review.

## D11 — Frontend: one generic `ContactEntryList` component

**Decision**: A single `ContactEntryList.vue` renders one entry type's list — value, primary marker, add input, per-entry edit/mark-primary/remove controls, and the validation message from the last failed action — parameterized by props (heading, empty-state text, API base path like `/api/people/42/emails`). `PersonDetailPage` mounts it twice (emails, phones) alongside the contact-less edit form. `PeoplePage` rows read the primary entry from the arrays for the email and phone cells, empty cell when none.

**Rationale**: The two types have identical interaction models by design (US2 explicitly mirrors US1), so one component keeps the phone story to configuration plus tests. Server responses returning the refreshed list (D7) let the component stay stateless-ish: render what the server confirms, which is also what makes the reload-persistence scenarios trivially true.

**Alternatives considered**: Separate `EmailList`/`PhoneList` components — duplication with no divergent behavior to justify it. Editing entries via modal — inline editing matches the spec's "edits an address in place" wording and the app's form-first style.
