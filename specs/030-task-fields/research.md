# Phase 0 Research: task-fields

No open technology unknowns — this feature extends the existing Fastify + Drizzle/SQLite + Vue 3 + `@modelcontextprotocol/sdk` stack with no new dependency. What follows resolves the design questions the spec explicitly leaves to `/speckit-plan` (the source PRD says "setting or clearing a field is illustrative UI mechanics for `/speckit-plan` to decide") plus the shape questions the spec's FRs imply but don't spell out.

## R1 — Column shape and migration

- **Decision**: Four new nullable columns on `tasks` (`src/server/db/schema.ts`): `dueDate: text('due_date')`, `priority: text('priority', { enum: ['Low', 'Medium', 'High', 'Urgent'] })`, `effort: text('effort', { enum: ['S', 'M', 'L', 'XL'] })`, `description: text('description')` — none `.notNull()`, none with a default, so they land as SQL `NULL` (unset) on every existing row with no migration/backfill logic (FR-013).
- **Rationale**: SQLite's `ALTER TABLE tasks ADD COLUMN <name> text` (nullable, no default) is metadata-only — it does not rebuild the table or touch any existing column, so every pre-existing task's four new fields become `NULL` at zero data-loss risk. This is the same non-destructive `ALTER TABLE ... ADD` shape already used for `tasks.archived` in `card-archive` and `people.company_id` in `0003_dazzling_eternity.sql`. Drizzle's `enum` option on a SQLite `text()` column is app-layer typing only (confirmed by the existing `email_messages.importance`/`flag_status` columns, which generate plain `text` with no `CHECK` constraint) — actual value enforcement happens via `zod`, not the database.
- **Alternatives considered**: A separate `task_fields` side table — rejected as unrequested complexity for four scalar, always-1:1 attributes with no independent lifecycle; every other task attribute (`title`, `lane`, `position`) already lives directly on `tasks`. A `NOT NULL DEFAULT ''`/sentinel-value approach for description — rejected; `null` cleanly represents "unset" and is what the detail view's "No description" state should check, matching how `people.companyId` already uses `null` for "no company."

## R2 — Due-date representation and validation

- **Decision**: `dueDate` is stored and transmitted as a plain `YYYY-MM-DD` string, produced by the UI's date picker and expected in the same shape from MCP callers (mirroring the acceptance scenario's `"2026-09-10"` example). No server-side format regex is added — the value is accepted and stored as-is, matching FR-002's "no value constraints beyond the fixed priority/effort lists" and the existing precedent that `email-sync`/`calendar-sync`'s `startDate`/`endDate` columns are plain, unvalidated `text` strings.
- **Rationale**: Over-validating the date's format wasn't requested and would add a constraint the spec explicitly disclaims ("any date accepted"). Display formatting is a client concern: a new `formatDueDate()` util parses `YYYY-MM-DD` into a nice string ("Aug 20, 2026") and falls back to rendering the raw string if it doesn't parse — so a well-formed value (the only kind the UI's own picker can ever produce) always renders nicely, and a malformed value from an external MCP caller degrades gracefully instead of crashing the detail view or card face.
- **Alternatives considered**: Storing as an epoch-ms integer (like `calendarEvents.startAt`) — rejected; those columns represent a specific instant (with time), while a due date is explicitly "no time component" (FR-001), and round-tripping a date-only value through a timestamp risks timezone-shift bugs (the exact class of bug `SyncPage.vue`'s existing `parseLocalDate`/local-midnight helpers work around for its own date pickers). A strict `z.string().regex(/^\d{4}-\d{2}-\d{2}$/)` schema — rejected as an unrequested value constraint that FR-002 explicitly rules out.

## R3 — Editing UX: inline auto-save vs. explicit save

- **Decision**: Due date, priority, and effort each render as an always-visible control (an `NDatePicker`/`NSelect`, clearable) that saves immediately on change — no separate save button, no confirmation step. Description renders as rendered markdown with an "Edit" control that reveals a raw-text textarea plus explicit "Save"/"Cancel" buttons.
- **Rationale**: The three structured fields are single-click/single-selection changes, and this codebase's precedent for that shape of interaction is uniformly immediate: lane pills (`TaskDetail.vue`'s `moveToLane`), tag attach/detach (`TagInput.vue`), and archive/unarchive (`archiveCard`/`unarchiveCard`) all fire on click with no confirmation and no separate save step. Description is qualitatively different — free-form multi-line text where per-keystroke or per-blur autosave would be noisy (many small writes, easy to trigger a save mid-thought) — so it follows the codebase's other precedent for exactly this shape: `CompanyDetailPage.vue`'s rename control (view mode → "Edit" reveals an input + Save/Cancel → view mode). This also naturally distinguishes "no description" (rendered state shows the unset label, per FR-004) from "editing a description," which a bare always-visible textarea would blur.
- **Alternatives considered**: Autosave-on-blur for description — rejected; a stray click away from the textarea (e.g., to read something else on the page) would silently commit a half-finished edit with no way to cancel, unlike every other editable field in this app (note-adding, tag-adding, renaming) which requires a deliberate submit action.

## R4 — `update-task`'s tri-state field semantics, and folding rename into it

- **Decision**: `updateTaskTitle` is replaced by a single `updateTask(db, taskId, input)` service function accepting a partial patch: `{ title?: string; dueDate?: string | null; priority?: TaskPriority | null; effort?: TaskEffort | null; description?: string | null }`. For each of the four new fields, `undefined` (key omitted) means "leave unchanged," an explicit `null` means "clear," and a value means "set" — three states, not two. `title` keeps its own non-nullable-when-present semantics (renaming to an empty title is still rejected, matching today's `titleSchema`). The MCP `update-task` tool's `title` input becomes optional (previously required) so a fields-only call doesn't need to also rename; the four new fields are added as `<field>: <enumOrString>.nullable().optional()`.
- **Rationale**: FR-010 requires update-task to accept all four fields "in a single call, including the ability to explicitly clear a previously-set field" — that's impossible to express with a plain optional (`?: T`) alone, since an absent key and an intentionally-cleared key would be indistinguishable. This app already has exactly this pattern for `people.companyId` (`updatePersonInputSchema`'s `companyId: z.number().nullable().optional()`, and `set-person-company`'s `companyId: z.number().int().positive().nullable()`), so the four new fields follow the same, already-proven shape rather than inventing a new one (e.g., a sentinel string, or a separate `clearFields: string[]` array). Folding rename into the same tool (rather than adding a second `update-task-fields` tool) keeps one task-mutation entry point on MCP, consistent with `create-task` being the single entry point for task creation with all its optional inputs.
- **Alternatives considered**: A `clearDueDate: boolean` (and three siblings) alongside `dueDate?: string` — rejected as a clunkier, doubled input surface for the same tri-state need the nullable-optional shape already solves cleanly. Keeping `updateTaskTitle` separate and adding a second `update-task-fields` tool — rejected; the spec's acceptance scenario explicitly exercises "the MCP update-task tool changing all four fields in one call," implying one tool, one call.

## R5 — Enum validation for priority/effort (FR-012)

- **Decision**: `priority`/`effort` are registered as `z.enum(['Low', 'Medium', 'High', 'Urgent']).nullable().optional()` (and the effort equivalent) directly in the MCP tool's `inputSchema`. The `@modelcontextprotocol/sdk` validates tool input against this schema before the handler runs, so an out-of-range value (e.g., "Critical") is rejected with a validation error at the protocol layer, and the handler — and therefore `updateTask`/`createTask` — never even sees it, guaranteeing the task's existing values are left untouched (FR-012's "MUST NOT change the task's existing field values"). The HTTP `PATCH /api/tasks/:id` route defensively re-validates the same enum via `safeParse` before calling the service, returning 400 on failure.
- **Rationale**: This mirrors how every other constrained-value MCP input in this codebase already works (e.g., `add-contact-entry`'s `type: z.enum(['email', 'phone'])`) — no bespoke error-string matching or manual `if (!validValues.includes(...))` check is needed in the service layer, since the schema itself is the gate. The HTTP route needs its own check because, unlike the MCP SDK, Fastify doesn't auto-validate a route body against a zod schema in this codebase (see `routes/tasks.ts`'s existing manual `placementIndexSchema.safeParse` pattern) — and a public HTTP endpoint can't assume the client is the trusted `NSelect`-constrained UI.
- **Alternatives considered**: Validating priority/effort only inside `updateTask`/`createTask` (service layer) and letting the MCP `inputSchema` accept a bare `z.string()` — rejected; that would mean an invalid value reaches the handler and requires hand-written rejection logic duplicating what zod's `enum` already does for free, and would diverge from this codebase's established pattern.

## R6 — What the card face shows, and where that data comes from

- **Decision**: `TaskCard.vue` renders a plain due-date badge (`data-testid="due-date-badge"`) when `task.dueDate` is non-null, using the same `formatDueDate()` util as the detail view, and nothing else — no priority/effort/description indicator (FR-008). No new endpoint or query is needed: `GET /api/board` already returns whole `tasks` rows via `listBoardTasksByLane`'s `{ ...task, tags, searchText }` spread (`services/tasks.ts`), so the four new columns arrive in the existing board payload automatically once they exist on the table and on the shared `Task`/`BoardTask` TypeScript interfaces — this is a pure client-side rendering addition, matching the same "already-fetched, just render it" shape `card-archive`'s dimmed-style/badge addition used for `archived`.
- **Rationale**: Keeps the change vertical and minimal — no server code change is needed to expose `dueDate` to the board view beyond the schema/type edits already required for every other surface.

## R7 — MCP field surface: threading the four fields through every task-shaped output

- **Decision**: `dueDate`, `priority`, `effort`, `description` are added once to the shared `taskSummarySchema` object (`src/server/mcp/tools.ts`) and once to `taskDetailContent()`. Because `taskDetailOutputSchema` already spreads `taskSummarySchema`, `get-task`'s output gains the four fields with no schema change of its own beyond that one shared object. Every place that currently hand-maps a task row into `structuredContent` (`create-task`, `update-task`, `move-task`, `archive-card`, `unarchive-card`, and `list-board`'s per-task mapping) gets the four fields added explicitly, copied straight from the row.
- **Rationale**: Identical reasoning to `card-archive`'s R5, which threaded `archived` through the same set of hand-built mappings for the same structural reason — these four fields are now core, always-present task attributes (present-but-possibly-null, like `archived` is present-but-boolean), and every existing task-returning tool should honestly report them rather than special-casing which tools do.
- **Alternatives considered**: A separate `taskFieldsSchema` object merged only into `get-task`'s output — rejected; that would leave `list-board`, `create-task`, and `update-task` silently omitting data SC-003 requires to be visible from MCP ("a value set via the UI is returned correctly by MCP query tools... with no discrepancy in 100% of checked cases"), which explicitly includes the board-listing tool, not just `get-task`.
