# Research: Email Sync

**Feature**: 007-email-sync | **Date**: 2026-08-08

All NEEDS CLARIFICATION items from the Technical Context, plus the two decisions the spec explicitly deferred to `/speckit-plan` (mailbox auth mechanism, simulated-mailbox mechanism), are resolved below.

## R1. Mailbox authentication: MSAL Node device-code flow with a persistent file token cache

- **Decision**: Use `@azure/msal-node` (public client application) with the OAuth 2.0 device code flow, delegated scope `Mail.Read` (plus `offline_access`), authority `https://login.microsoftonline.com/common` (works for both personal Outlook.com and work/school accounts). The MSAL token cache is serialized to a file (default `./data/mail-token-cache.json`, override via `MAIL_TOKEN_CACHE_PATH`) via MSAL's cache plugin, so the refresh token survives restarts and lives on the Docker volume alongside the SQLite DB. One-time interactive sign-in runs from the server host as an npm script: `npm run mail:signin` (a `tsx` CLI at `scripts/mail-signin.ts`) prints the `https://microsoft.com/devicelogin` URL + code, waits for completion, and writes the cache. Sync itself always calls `acquireTokenSilent`; if that fails (cache missing/invalidated), the sync tool fails with a clear "mailbox sign-in required — run npm run mail:signin" error and the store is untouched (FR-016). Requires a one-time Entra ID app registration supplying `MS_CLIENT_ID` (documented in quickstart).
- **Rationale**: Device code flow is the standard interactive-once/headless-after pattern for a self-hosted server with no browser; MSAL handles refresh, cache serialization, and MSA-vs-AAD differences. Matches the spec assumption "one-time interactive sign-in run from the server, after which cached credentials keep sync working unattended".
- **Alternatives considered**: Client-credentials (app-only) auth — rejected: not available for personal Microsoft accounts and grants org-wide mailbox access on work tenants; wildly over-scoped for one mailbox. Auth-code flow through the work-helper web UI — rejected: adds redirect-URI/HTTPS setup and UI surface for a one-time operation; the CLI is smaller and the spec allows it. Hand-rolled OAuth with raw fetch — rejected: re-implements refresh/cache logic MSAL provides for free.

## R2. Graph API access: native `fetch` against Graph REST v1.0, no Graph client SDK

- **Decision**: Call Microsoft Graph REST v1.0 directly with Node 22's built-in `fetch` from a `GraphMailProvider`. Per folder, page through `GET /v1.0/me/mailFolders/{inbox|sentitems}/messages` with `$select=id,conversationId,subject,body,sentDateTime,receivedDateTime,from,toRecipients,ccRecipients,bccRecipients`, `$filter` on the folder's timestamp field (R4), `$orderby` on that same field, `$top=100`, following `@odata.nextLink` until exhausted. Send `Prefer: IdType="ImmutableId"` on every request so message ids are stable across mailbox moves, and store that immutable id as the dedupe key (FR-004). All requests are GETs — the feature never writes to the mailbox (FR-015).
- **Rationale**: The needed surface is two paged GET endpoints; the official `@microsoft/microsoft-graph-client` SDK adds a dependency tree for what `fetch` + a URL builder does in ~50 lines, and a thin provider is easier to fake in tests (R6). Immutable ids are Graph's documented answer to "default message ids change when a message moves folders" — exactly the failure mode that would break idempotent re-sync.
- **Alternatives considered**: `@microsoft/microsoft-graph-client` — rejected as unneeded weight; its middleware (retry, auth) duplicates what the provider seam already owns. Graph delta queries (`/delta`) — rejected for this slice: delta is built for continuous incremental sync (the `email-sync-automation` stub), while this slice's contract is an explicit date-range pull; `$filter` on a range is simpler and matches FR-002 directly. `internetMessageId` as the dedupe key — rejected as primary key (kept out of scope entirely): immutable id is per-mailbox-item, which correctly treats e.g. the Inbox and Sent copies of a self-addressed message as the two distinct items they are.

## R3. Conversation grouping: trust Graph's `conversationId`

- **Decision**: Group stored messages by the Graph `conversationId` field verbatim: find-or-create an `email_conversations` row keyed by unique `graph_conversation_id`, attach each message to it. Later syncs that pull messages carrying an already-stored `conversationId` join the existing conversation (FR-006, edge case "message joins the existing conversation").
- **Rationale**: The spec assumption says "Conversation grouping trusts the mailbox's own thread identity rather than inferring threads from subjects or headers", and `conversationId` is that identity in Graph — it already groups Sent replies with Inbox counterparts.
- **Alternatives considered**: Subject-normalization or `References`/`In-Reply-To` header threading — rejected: explicitly ruled out by the spec assumption, and strictly worse than the mailbox's own grouping.

## R4. Range semantics: local-day window on `receivedDateTime` (Inbox) / `sentDateTime` (Sent)

- **Decision**: The tool takes `startDate`/`endDate` as `YYYY-MM-DD` strings. The window is `[new Date(y, m, d)` of startDate, `new Date(y, m, d) + 1 day` of endDate`)` — i.e. local midnight to local midnight-after-end in the server's timezone — converted to UTC ISO for the Graph `$filter` (`ge {startIso} and lt {endIso}`). Inbox filters/sorts on `receivedDateTime`; Sent Items on `sentDateTime`. The stored `sent_at` epoch-ms timestamp is that same folder-appropriate field, and it drives all ordering in the read tools.
- **Rationale**: Matches the clarification "endpoint days are whole days in the work-helper server's local timezone" and the edge case (23:30 local on the end day is in range despite being next-day UTC). `receivedDateTime` is when mail landed in the Inbox; `sentDateTime` is when Sent mail left — each is the natural "the message's timestamp" for its folder and both are filterable in Graph.
- **Alternatives considered**: Filtering both folders on `receivedDateTime` — rejected: on Sent items the meaningful timestamp is when it was sent; the two are near-identical there, but `sentDateTime` states the intent. Accepting full ISO datetimes as range inputs — rejected: the spec's contract is whole days.

## R5. Body storage: original body verbatim + `html-to-text` derived plain text

- **Decision**: Store `body.content` and `body.contentType` (`html` | `text`) exactly as Graph delivers them, plus a derived `body_text` column produced at ingest: for `text` bodies it is the content as-is; for `html` bodies it is the output of the `html-to-text` npm package (links kept inline, default wrapping disabled). Read tools return only `body_text` (FR-008); the original is retained for future slices (email UI stub) and never returned or rendered here.
- **Rationale**: Matches the clarification ("store the original body exactly as the mailbox delivered it plus a derived plain-text version; the read tools return the plain text"). `html-to-text` is the established, actively maintained converter with no DOM/browser dependency; deriving at ingest (not read time) keeps reads cheap and makes the snapshot self-contained.
- **Alternatives considered**: Requesting `Prefer: outlook.body-content-type="text"` from Graph — rejected as the *only* stored form (loses the original), and requesting both forms means a second fetch per message; local conversion is one pass. `turndown` (HTML→Markdown) — rejected: tools promise plain text, not Markdown. Regex tag-stripping — rejected: mangles entities, tables, and quoted replies.

## R6. Simulated mailbox for automated acceptance: a `MailProvider` seam with a fake implementation

- **Decision**: Define a `MailProvider` interface in the server (`fetchMessages(folder, windowUtc): AsyncIterable<MailMessage[]>` yielding pages of a normalized `MailMessage` shape mirroring the Graph fields we `$select`). Two implementations: `GraphMailProvider` (R2) wired in `src/server/index.ts` for real runs, and a test-owned `FakeMailProvider` seeded with in-memory messages (folder, timestamps, conversation ids, recipients) that integration tests inject via `buildApp` options. The fake can be told to throw mid-pagination to exercise the interrupted-sync path (FR-016). Automated acceptance scenarios run the full real stack — Fastify app, OAuth'd MCP client, SQLite — with only the mailbox faked. `GraphMailProvider` itself gets focused unit tests (URL/filter/Prefer-header construction, nextLink paging, error mapping) against stubbed fetch responses with Graph-shaped fixtures.
- **Rationale**: The spec defers the simulation mechanism to the plan and requires seeded-mailbox tests. An interface seam at the provider boundary keeps the entire ingest pipeline (dedupe, threading, addresses, transactions) under real test coverage while faking only the network edge — the same pattern the existing tests use for everything else (real app + real DB, in-memory). It also enables TDD: sync tests are written against the seam before Graph code exists.
- **Alternatives considered**: An HTTP-level fake Graph server the real provider points at — rejected: more moving parts for marginal extra fidelity, and the provider's request-building fidelity is covered by its own unit tests. Recording/replaying real Graph traffic — rejected: fixtures rot, contain real mail, and can't express the seeded scenarios the acceptance criteria specify.

## R7. Shared email-address model: `person_emails` becomes `email_addresses` with nullable `person_id`

- **Decision**: Restructure the existing `person_emails` table into `email_addresses`: same columns plus `person_id` becomes **nullable** (an address with `person_id = NULL` is an unlinked record seen only in synced mail). Case-insensitive uniqueness (`lower(value)` unique index) is kept and now serves as the ingestion dedupe (FR-009). Behavior rules, enforced in the services: (a) ingest find-or-creates by lowercased value and never touches `person_id` (FR-010 — no auto-linking creation of people; matching to a person is just the stored `person_id`); (b) People-page add: if the value exists unlinked → link that record (set `person_id`, primary if the person has no other email) instead of inserting; if it exists linked to anyone → conflict, exactly today's rejection (FR-011/FR-012); (c) People-page remove: if the address is referenced by any participant → unlink (`person_id = NULL`, `is_primary = false`) so the snapshot keeps its address record; otherwise delete the row (today's behavior); (d) person deletion applies rule (c) to each of the person's addresses. Participants FK-reference `email_addresses` with no cascade, so the DB itself refuses to delete an address a snapshot depends on.
- **Rationale**: The spec's Key Entities require one shared address record used by both the People page and ingestion, unique case-insensitively, belonging to at most one person or none. The current table is 90% of that — only the NOT NULL + cascade-delete semantics conflict with "or none" and with snapshot permanence (FR-003).
- **Alternatives considered**: A separate `email_addresses` table for ingestion joined to `person_emails` — rejected: creates exactly the parallel-records problem FR-009 forbids. Auto-linking by creating people for unknown addresses — explicitly out of scope in the spec.

## R8. Schema change mechanics: squash to a single base migration, reset dev DBs, drop the carry-over test

- **Decision**: Follow the constitution's development-phase data policy literally: edit `src/server/db/schema.ts` in place (restructured `email_addresses` + three new tables), delete the accumulated `drizzle/` migration files and regenerate a single fresh `0000_*` baseline with `drizzle-kit generate`, and recreate dev databases (`rm -f data/*.db`; tests use `:memory:` and are unaffected). `tests/integration/migration-carry-over.test.ts` is deleted in the same change: it verifies feature 005's data-preserving migration path by replaying the now-removed migration files 0000–0004, which is precisely the kind of migration-path maintenance the constitution says not to carry during the no-real-data phase.
- **Rationale**: Constitution "Additional Constraints": *"do not accumulate migration files... apply schema changes by editing the base schema in place and resetting/recreating the dev database freely"*. Adding a sixth migration (with a NULL-able rebuild of `person_emails`, a rename, and a data copy) would build exactly the backfill machinery the policy forbids. `createDb` keeps calling `migrate()` unchanged — it just applies the one baseline to fresh/in-memory DBs.
- **Alternatives considered**: Additive migration 0005 preserving `person_emails` data — rejected: violates the stated policy and spends effort on a migration path with no data to preserve. Renaming the table back to `person_emails` while making `person_id` nullable — rejected: the name would misdescribe the entity the spec defines (a shared address record, not a person attribute); the code churn of the rename is confined to the contact-entries service and schema imports.

## R9. Read-tool pagination: opaque keyset cursors

- **Decision**: `list-conversations` orders by `(latestMessageAt DESC, conversationId DESC)`; `emails-for-person` orders by `(sentAt DESC, messageId DESC)`. Both accept `limit` (1–200, default 50) and `cursor`; the returned `nextCursor` is a base64-encoded JSON of the last row's sort key, and the next page filters strictly-after that key. `nextCursor` is present only while more rows remain. `get-conversation` is unpaged by design (clarification) and returns messages in `(sentAt ASC, messageId ASC)` order.
- **Rationale**: Keyset pagination is stable under concurrent inserts in the way FR-007/FR-013 require ("paging through returns every conversation/email exactly once") — offset paging shifts when a sync lands mid-pagination. Deterministic id tiebreakers make ordering total even with equal timestamps.
- **Alternatives considered**: Offset/limit — rejected: skips or repeats rows when rows are inserted between pages. Snapshot-token pagination (materialized page state) — rejected: server-side state for a single-user tool is overkill.

## R10. Sync failure semantics: per-message transactions, structured interrupted result

- **Decision**: Each message is ingested in its own SQLite transaction (find-or-create conversation → insert message → find-or-create addresses → insert participants). A message already stored (by `graph_message_id`) is skipped before any writes and never recounted (FR-004/FR-005). If the provider throws before anything was stored in the run and the cause is auth/connectivity, the tool returns a tool error identifying the connection problem (store untouched); if it throws mid-run, everything already committed stays, and the tool returns a structured `{ status: "interrupted", syncedCount, error }` result — re-running the same range skips the stored prefix and completes the rest (FR-016, clarification on partial progress).
- **Rationale**: Per-message transactions make "keep partial progress" and "no duplicates on retry" fall out of the storage design instead of requiring compensation logic; better-sqlite3's synchronous transactions make this cheap.
- **Alternatives considered**: One transaction per sync run — rejected: rolls back partial progress, contradicting the clarification. A sync-run ledger table for resumability — rejected: idempotent skip-by-id already makes retry correct; the ledger adds state without adding a capability.

## R11. Performance sanity check (SC-006: one-month real-mailbox sync < 5 minutes)

- **Decision**: No special performance work. Budget: a heavy personal-mailbox month is a few thousand messages; at `$top=100` that is tens of sequential Graph page requests (each well under a second) and per-message SQLite work measured in microseconds–milliseconds. Even 5,000 messages fits in well under 5 minutes with a single sequential loop, so no parallel fetching, batching beyond Graph paging, or progress checkpointing is added.
- **Rationale**: Meeting SC-006 with the simplest sequential design keeps the interrupted-sync semantics (R10) easy to reason about.
- **Alternatives considered**: Parallel folder/page fetching — rejected: complicates failure attribution for interrupted syncs and isn't needed for the budget.
