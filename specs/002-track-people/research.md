# Research: Track People

**Branch**: `002-track-people` | **Date**: 2026-08-06

All unknowns flagged during Technical Context drafting, resolved against the existing codebase and the spec's assumptions. No NEEDS CLARIFICATION remain.

## R1. Field configuration mechanism (format & location)

- **Decision**: `config/person-fields.json` — a JSON array of extra field labels, e.g. `["Nickname"]`. Loaded at startup by a new `src/server/person-fields-config.ts` (`loadPersonFieldsConfig()`), validated with Zod, decorated onto the Fastify app as `app.personFields`, and exposed to the client via `GET /api/person-fields`. An empty array `[]` is valid (no extra fields). Entries must be non-empty after trimming, unique, and must not collide case-insensitively with the built-in labels ("First name", "Last name", "Email", "Phone") to avoid two same-named inputs on the form.
- **Rationale**: The spec's assumption says the mechanism "follows the same pattern as the kanban lane configuration". `src/server/lanes-config.ts` reads `config/lanes.json` (a JSON string array) with a Zod schema, an env override (`LANES_CONFIG_PATH`), and fail-fast errors; mirroring it (`PERSON_FIELDS_CONFIG_PATH` override) keeps one config idiom in the repo. A flat label array is sufficient because extra fields are free-text-only and always optional (FR-009) — there is nothing else to configure per field.
- **Alternatives considered**: Objects with `{ key, label, type }` — rejected: YAGNI while only optional free-text exists; a richer shape can be introduced by a later feature without breaking a string array. Database-stored field definitions — rejected: FR-011 forbids in-app management; a file edited outside the app is exactly the lanes precedent. Env var — rejected: awkward for lists, breaks the established pattern.

## R2. Storage of extra field values

- **Decision**: A JSON text column on `people` — `extra_fields text NOT NULL DEFAULT '{}'` using Drizzle's `text('extra_fields', { mode: 'json' }).$type<Record<string, string>>()`. Keys are the configured labels exactly as written in the config; values are trimmed non-empty strings (blank inputs are omitted, satisfying "extra fields are always optional"). On read, only keys present in the *current* configuration are surfaced to forms/records; stale keys from a since-removed field stay in the column harmlessly.
- **Rationale**: Nothing queries extra fields — the linked-people search is spec-limited to first name, last name, and email (FR-013), and extra fields never appear as list columns (out of scope). With no relational access pattern, a JSON map is the simplest thing that persists per-person values (FR-009, SC-007) and adapts automatically when the config gains a field.
- **Alternatives considered**: EAV table `person_field_values(person_id, field, value)` — rejected: adds a join and cascade handling for values that are only ever read/written whole-person; relational form buys nothing without queries against it. One real column per configured field with migrations on config change — rejected outright: config edits must not require schema migrations (FR-009's "without any code change" spirit).

## R3. Email uniqueness (case-insensitive, non-blank only) & referential integrity

- **Decision**: Two layers.
  1. *Service layer* (authoritative UX): on create/update, if the normalized email is non-null, query for another person with `lower(email) = lower(?)` and `id != ?`; on a hit, fail with the exact message "That email is already in use" (409). Blank/whitespace email is normalized to `NULL` before this check, so blanks never conflict (FR-004) and a person never conflicts with themselves (`id != ?`).
  2. *Database backstop*: partial unique expression index `CREATE UNIQUE INDEX people_email_unique ON people (lower(email)) WHERE email IS NOT NULL`, declared in Drizzle schema as `uniqueIndex('people_email_unique').on(sql`lower(${t.email})`).where(sql`${t.email} IS NOT NULL`)`. SQLite supports expression + partial indexes; if drizzle-kit's generator mishandles the expression, the statement is appended to the generated migration SQL by hand (migrations are plain `.sql` files in `drizzle/`).

  Additionally, `createDb()` gains `sqlite.pragma('foreign_keys = ON')` — better-sqlite3 does not enable foreign-key enforcement by default, and the new `task_people` table relies on `ON DELETE CASCADE` so deleting a person removes every task link in one statement (FR-008, SC-006).
- **Rationale**: The service check produces the spec's friendly validation message and leaves existing records unchanged; the index makes the invariant hold even against future code paths. Normalizing blank → `NULL` makes "only non-blank emails conflict" fall out of the index's `WHERE` clause naturally. The pragma is a one-line prerequisite for trusting CASCADE at all.
- **Alternatives considered**: `email text COLLATE NOCASE` unique column — rejected: SQLite unique treats multiple NULLs as distinct (fine) but a plain unique on the column can't express "ignore blanks" if blanks were stored as `''`, and NOCASE collation on the column changes comparison semantics everywhere, not just uniqueness. Application-only check with no index — rejected: no integrity backstop. Doing cascade deletes manually in a transaction instead of FK CASCADE — kept as the shape of the service code anyway (single `delete person` call), but FK enforcement is still turned on so the schema states the invariant.

## R4. Client navigation; task detail and person record as pages vs modals

- **Decision**: Add `vue-router@4` (the official router for Vue 3) — the feature's only new dependency. Routes: `/` (board, existing UI moved into `BoardPage.vue`), `/people` (directory + create form), `/people/:id` (person record/edit), `/tasks/:id` (task detail). The task detail view and person record are **routed pages, not modals**. `App.vue` becomes a shell with a Board | People nav and `<RouterView>`. `TaskCard.vue` navigates to `/tasks/:id` on click; its rendered face is unchanged (FR-017).
- **Rationale**: The app currently has exactly one screen and no routing; this feature adds three more screens, which is precisely the router's job. Pages beat modals here: each acceptance scenario starts "the People page is open" / "the task detail view is open", and URL-addressable views give the `browser-tester` agent direct, reload-stable entry points (several scenarios hinge on "survives a page reload"). The spec explicitly allows either; pages are the simpler and more testable choice.
- **Alternatives considered**: Hand-rolled `ref`-based view switching — rejected: no URLs, so reload-persistence scenarios would always land back on the board, and every future feature would re-pay the cost. Modal task detail over the board — rejected: more component state, no deep link, no reload story. Hash-based mini-router — rejected: vue-router is standard, small, and Vite/vue-tsc-friendly; hand-rolling saves one dependency at the cost of edge cases (history, active links).

## R5. Linked-people search implementation

- **Decision**: Server-side filter on `GET /api/people?q=...`: `instr(lower(first_name), lower(?)) > 0 OR instr(lower(last_name), lower(?)) > 0 OR instr(lower(coalesce(email, '')), lower(?)) > 0`, with `q` trimmed; absent/blank `q` returns the full directory. Results keep the directory's alphabetical order. The client's `LinkedPeople` widget debounces input and only queries for non-blank text; each result row shows name and email (FR-013).
- **Rationale**: `instr` + `lower` implements case-insensitive *substring* matching exactly as FR-013 demands, with no wildcard semantics — a typed `%` or `_` matches literally, which `LIKE` would misinterpret unless escaped. Reusing the list endpoint keeps one code path for shaping people. SQLite's `lower()` is ASCII-only, which matches the spec's scope (`"sam"` → "Sam Rivera") and the existing app's plain-ASCII data.
- **Alternatives considered**: `LIKE '%q%' COLLATE NOCASE` — rejected: requires escaping `%`/`_` in user input to stay literal. Client-side filtering of the full list — rejected: duplicates matching rules in two languages and drifts from FR-013's single definition; the server already owns list shaping. FTS5 — rejected: personal-CRM scale needs no index.

## R6. Link / unlink API semantics

- **Decision**: `task_people(task_id, person_id)` with composite primary key. `POST /api/tasks/:id/people` body `{ personId }` inserts with `onConflictDoNothing()` — linking an already-linked person is a silent no-op, so a task can never list the same person twice (FR-014, edge case). `DELETE /api/tasks/:id/people/:personId` deletes the pair; unlinking a not-linked person is likewise a no-op. Both return the updated task detail (same shape as `GET /api/tasks/:id`) so the client re-renders from one response; unknown task or person → 404. Linked people are returned sorted the same way as the directory (last name then first name, case-insensitive) — links are unordered per spec, so a stable, familiar order is chosen for display.
- **Rationale**: The composite PK makes at-most-one-link-per-pair a schema invariant rather than a code promise; idempotent link/unlink makes the "already linked" edge case unexciting on both client and server. Returning the task detail matches the existing style of returning the affected resource (`POST /api/tasks` returns the task) and saves a follow-up fetch.
- **Alternatives considered**: 409 on duplicate link — rejected: the spec frames re-selecting an already-linked person as a must-not-duplicate edge case, not an error the user should see. Surrogate `id` column on the join table — rejected: composite PK is the constraint itself; nothing references a link row. Returning 204 and refetching — rejected: two round-trips for every link action with no benefit.

## R7. People list ordering

- **Decision**: `ORDER BY last_name COLLATE NOCASE ASC, first_name COLLATE NOCASE ASC` applied in SQL for every people listing (directory, search results, linked people).
- **Rationale**: FR-001 fixes alphabetical-by-last-name; the spec's assumption adds case-insensitivity and first-name tiebreak. Doing it in SQL keeps one authoritative ordering (SC-002's reload consistency) instead of per-view client sorts. `COLLATE NOCASE` in `ORDER BY` affects only this query — unlike declaring it on the column (see R3).
- **Alternatives considered**: Client-side `Array.sort` — rejected: three views would each need the identical comparator. Ordering by `lower(...)` expression — equivalent; `COLLATE NOCASE` states the intent more directly.

## R8. Error and status conventions

- **Decision**: Keep the existing envelope `{ error: { message } }` (set by `app.setErrorHandler` / route handlers). Statuses: `400` missing/blank required names (message "First and last name are required"), `409` email already in use (message "That email is already in use"), `404` unknown person or task (messages "Person not found" / "Task not found"), `201` create person, `200` reads/updates/link/unlink, `204` delete person. No email *format* validation — the spec never requires it, so any non-blank string is a legal email value.
- **Rationale**: Matches the shipped create-task contract (`400` + `{ error: { message: 'Title is required' } }`), which the client already knows how to render. `409` distinguishes "valid input, conflicting state" from malformed input, and the exact messages satisfy SC-003's "names the problem". Skipping format validation honors the spec boundary — inventing stricter rules would reject data the spec says to accept.
- **Alternatives considered**: `400` for the email conflict too — workable, but conflates two failure kinds the UI words differently anyway. Per-field error maps — rejected: the form shows one message per failed save in the current UI idiom; a richer error shape can come with a feature that needs it.
