# Research: Home Server Deploy

**Feature**: 006-home-server-deploy | **Date**: 2026-08-07

All spec clarifications were resolved during `/speckit-specify`; the unknowns below are the implementation-shaping decisions, resolved by codebase inspection and (where noted) empirical Docker probes run on Docker 29.4.

## R1. Stack topology: one container

- **Decision**: The compose stack runs a single service, `work-helper`, containing the Fastify server which serves the built Vue client, the REST API, and the MCP endpoint on one in-container port.
- **Rationale**: The app is already a single Node process with embedded SQLite (better-sqlite3) — there is no database server or separate frontend to orchestrate. `buildApp({ serveClient: true })` already serves `dist/client` via `@fastify/static`, which is exactly the spec's "one port serving both" requirement (FR-003).
- **Alternatives considered**: Separate DB container (rejected — SQLite is embedded, a DB service would be invented complexity); separate nginx/UI container (rejected — duplicates what `serveClient` does and would need a second port or an internal proxy).

## R2. Image build: multi-stage on `node:22-bookworm-slim`

- **Decision**: Multi-stage `Dockerfile`, both stages on `node:22-bookworm-slim`. Builder: install build essentials (`python3 make g++` — insurance for compiling better-sqlite3 if no prebuilt binary matches), `npm ci`, `npm run build` (vite → `dist/client`, `tsc -p tsconfig.server.json` → `dist/server-build`), then `npm prune --omit=dev`. Runtime: copy `node_modules`, `dist/`, `drizzle/`, `config/`, `package.json`; install `procps` (provides `pkill`, needed by the crash-recovery check and useful for ops); `ENV NODE_ENV=production PORT=8080`; `CMD ["node", "dist/server-build/server/index.js"]`; `WORKDIR /app`.
- **Rationale**: `engines.node >= 22` pins the major. Debian slim (glibc) is the safest base for the better-sqlite3 native module; the builder toolchain makes the build deterministic even when no prebuild exists for the server's architecture (deploys build on-server per PRD, so the arch is whatever Tyler's server is). `drizzle/` must ship in the image because `createDb` runs `migrate(db, { migrationsFolder: 'drizzle' })` relative to the working directory at startup. `config/` ships as an in-image fallback; compose bind-mounts the host's `./config` over it (R5). `dist/client` is resolved from `process.cwd()` by `serveClient`, hence `WORKDIR /app` and copying `dist/` there.
- **Alternatives considered**: `node:22-alpine` (rejected — musl adds native-module risk for no meaningful gain on a home server); distroless runtime (rejected — no shell blocks the `docker exec pkill` crash simulation in R6 and everyday debugging); prebuilt registry images (out of scope by PRD decision).

## R3. Port scheme: fixed 8080 inside, `WORK_HELPER_PORT` outside

- **Decision**: The container always listens on 8080 (`PORT=8080` baked into the image; `src/server/index.ts` already reads `PORT`). Compose publishes `"${WORK_HELPER_PORT:-8080}:8080"`. The Caddy snippet's upstream is `work-helper:8080`.
- **Rationale**: Satisfies the clarified default (host port 8080, `.env`-overridable) while keeping the container-internal port constant, so overriding the host port never invalidates the documented Caddy snippet — Caddy talks to the container port over the shared network, not the published one. A distinct variable name (`WORK_HELPER_PORT`, not `PORT`) keeps the operator-facing knob unambiguous in `.env`.
- **Alternatives considered**: Reusing `PORT` for the host mapping (rejected — one name meaning two different ports invites misconfiguration); host networking (rejected — non-portable to Docker Desktop and defeats the shared-network-by-name design).

## R4. Fail-fast on missing settings (FR-011): compose interpolation + app validation

- **Decision**: Two layers. (1) `compose.yaml` references the password as `${CONNECTOR_PASSWORD:?CONNECTOR_PASSWORD is required — create .env from .env.example}` so `docker compose up` aborts before starting any container, with an error naming the setting — this covers both a missing `.env` and a missing value, because compose reads `.env` natively. (2) A new `src/server/env.ts` validates at startup: when `NODE_ENV=production` and `CONNECTOR_PASSWORD` is unset/empty, log a clear error naming the setting and exit non-zero. Dev behavior is unchanged (no password → MCP endpoints answer "unconfigured", as today).
- **Rationale**: Compose interpolation gives the earliest, clearest operator error with zero code; the app-level check is unit-testable (constitution II) and protects any non-compose invocation of the production build. No dotenv dependency is added — compose is the `.env` reader, matching "Docker is the only prerequisite".
- **Alternatives considered**: App-level only (rejected — the error would be buried in container logs after `up -d` returns success, failing "fail fast with a clear error"); compose-level only (rejected — untestable in vitest and silently lost if the image is ever run without compose).

## R5. Persistence & config: bind mounts of `./data` and `./config`

- **Decision**: `compose.yaml` bind-mounts `./data:/app/data` and `./config:/app/config`. No `DATABASE_PATH`/`LANES_CONFIG_PATH`/`PERSON_FIELDS_CONFIG_PATH` env needed — the code's defaults (`./data/work-helper.db`, `config/lanes.json`, `config/person-fields.json`) resolve against `WORKDIR /app` and land exactly on the mounts. `.dockerignore` excludes `data/` so user data can never bake into an image layer.
- **Rationale**: Matches the clarification (bind-mounted host directory, ordinary files, in the clone alongside the mounted config directory — FR-004, US6). `createDb` already `mkdirSync`s the data directory and runs migrations at startup, so a first `up` on an empty `./data` self-initializes, and container rebuilds only ever swap the process around the files.
- **Alternatives considered**: Named volume (rejected by clarification — Tyler wants ordinary host files); mounting individual config files instead of the directory (rejected — file-level bind mounts break inode-based edits from common editors and complicate adding config files later).
- **Note**: The repo's tracked `config/*.json` are the mounted files; local edits on the server can collide with `git pull` during updates. The deploy doc will call this out (stash or commit local config edits before pulling). This is inherent to "config lives in the clone" from the clarification, not a design choice to revisit.

## R6. Crash recovery (FR-006): `restart: unless-stopped` + `init: true`, crash simulated in-container

- **Decision**: The service gets `restart: unless-stopped` and `init: true`. The automated recovery check simulates a crash with `docker exec <container> pkill -9 node`, then polls the published port until the app responds again, asserting ≤ 30 s.
- **Rationale**: **Empirically verified on Docker 29.4** (probes run during planning): `docker kill` is treated as a manual stop — the container stays `exited`, `RestartCount` 0, restart policy does **not** fire. Killing the payload process inside a container running under `--init` (tini as PID 1) makes the container exit on its own, and the policy restarts it (`RestartCount` 1, `running`). So the test must kill the node process from inside — which also needs node to *not* be PID 1 (PID 1 ignores SIGKILL from its own namespace), hence `init: true`; `procps` in the runtime image supplies `pkill` (R2). `init: true` additionally gives correct signal handling and zombie reaping for free. Reboot auto-start rides on the Docker daemon starting on boot plus `unless-stopped` (spec assumption). No container healthcheck: the restart policy reacts to process exit, which is the failure mode in scope; monitoring is out of scope per PRD.
- **Alternatives considered**: `docker kill` as the test's crash trigger (rejected — verified to not trigger the restart policy, would test nothing); killing the host-side PID (rejected — impossible from macOS Docker Desktop where the daemon runs in a VM); a `restart: always` policy (rejected — `unless-stopped` respects an operator's deliberate `docker compose stop` across reboots, which is the right home-server behavior).

## R7. Shared Docker network with Caddy (FR-009): compose-managed network named `work-helper`

- **Decision**: `compose.yaml` names the default network `work-helper` (non-external). The deploy doc tells the operator to attach their existing Caddy container once: `docker network connect work-helper <caddy-container>`. The compose service name `work-helper` is a DNS alias on that network, so Caddy's upstream `work-helper:8080` resolves.
- **Rationale**: A compose-managed network keeps first deploy to literally one command (FR-001) — an `external: true` network would require a `docker network create` pre-step and fail a fresh deploy if absent. A fixed, documented network name makes the attach command copy-pasteable.
- **Caveat (documented, accepted)**: While an outside container (Caddy) is attached, `docker compose down` stops the stack but cannot remove the network and reports an "active endpoints" error. This is cosmetic — containers are already stopped and the next `up` reuses the network. The doc's update procedure avoids `down` entirely (pull + `up -d --build` recreates in place), and the troubleshooting section explains the warning for the times Tyler does run `down`.
- **Alternatives considered**: External pre-created network (rejected — breaks one-command first deploy); Caddy reaching the app via the published host port (rejected by clarification — upstream must be the container name on a shared network); adding a second, dedicated proxy network (rejected — two networks to explain, zero benefit for a single-app host).

## R8. Forwarded client IP (FR-010): already implemented, proven through a real Caddy

- **Decision**: No app change. `buildApp` already sets `trustProxy: true`, so Fastify's `request.ip` — the only key the lockout tracker uses — honors `X-Forwarded-For`. The Caddyfile snippet includes `header_up X-Forwarded-For {remote_host}` inside the `reverse_proxy` block, making explicit what Caddy already does by default (see CI-review finding below). The automated check proves the end-to-end behavior through a real `caddy:2-alpine` container rather than trusting the flags: two client containers with distinct network IPs hit the proxy; client A fails the password three times and is locked out; client B then succeeds with the correct password; a third case sends a rotating forged `X-Forwarded-For` on every attempt and is still locked out, proving the lockout holds against a hostile client through the documented setup.
- **Rationale**: The lockout keying (`request.ip` in `oauth-routes.ts`) and trust setting are feature-004 behavior the spec says not to change, only to verify deployed. Direct (non-proxied) clients send no `X-Forwarded-For`, so they are counted by their own address — the spec's bypass edge case.
- **CI-review finding (verified, not a real gap)**: a CI review raised the general reverse-proxy concern that `reverse_proxy` *appends* to an existing `X-Forwarded-For` rather than replacing it (true of nginx's default `proxy_add_x_forwarded_for`), which combined with `trustProxy: true` taking the leftmost (least-trusted) entry would let a client forge the header through the documented Caddy setup and defeat the lockout. Empirically verified against Caddy 2.11.3 (`docker run` a minimal reverse_proxy in front of a header-echoing server, sent a forged `X-Forwarded-For`): Caddy does **not** append here — by default it discards any client-supplied `X-Forwarded-For` and replaces it with the address it actually observed. The adversarial test above (rotating forged header, still locked out on attempt 3) confirms this against the real lockout path, not just a synthetic probe. The explicit `header_up X-Forwarded-For {remote_host}` line changes nothing functionally today; it's kept as self-documentation of a security-relevant property and insurance against a future Caddy version or config change altering the default.
- **Accepted residual risk (unchanged)**: `trustProxy: true` trusts every caller, so a *direct* client bypassing Caddy entirely could still forge `X-Forwarded-For` and be mis-attributed — there is no proxy in that path to sanitize it. The spec's edge case explicitly scopes support to the documented snippet ("the documented snippet is the supported configuration"), and narrowing trust to the Docker network CIDR would couple app config to Docker internals for a single-operator install. Documented, not fixed.

## R9. Deploy acceptance test harness: real compose lifecycle from a working-tree copy

- **Decision**: `tests/deploy/` is a vitest suite with its own config (`vitest.deploy.config.ts`: only `tests/deploy`, `fileParallelism: false`, `testTimeout` ≥ 180 s), run by `npm run test:deploy`, and excluded from the default `vitest.config.ts` so the Stop-hook gate (`npm test`) stays fast and Docker-free. The harness: (1) copies the working tree — `git ls-files --cached --others --exclude-standard` — into a scratch temp dir (fresh-clone-equivalent that still covers uncommitted work-in-progress, which a literal `git clone` would silently drop mid-TDD); (2) writes `.env` with the test password and a dynamically chosen free host port as `WORK_HELPER_PORT`; (3) runs `docker compose -p <unique-project-name>` commands in that dir; (4) tears down with `docker compose down -v --rmi local`, removes any test Caddy/client containers, and deletes the temp dir. Update-survival (US2 scenario 2) is simulated by modifying a source file in the copy and re-running `up -d --build` — the pull itself is git mechanics, not this feature's surface; what must be proven is that an image rebuild + container recreation preserves `./data`.
- **Rationale**: The spec's independent tests are phrased as real lifecycle operations ("run `docker compose down`", "force-killed", "runs its own Caddy container") — only shelling out to real Docker satisfies evidence-over-assertion. A temp copy keeps the developer's own `./data` and `./config` untouched and makes SC-001's "fresh clone, documented steps only" claim honest. Unique project names + dynamic ports keep parallel worktree sessions from colliding.
- **Alternatives considered**: Running compose against the worktree itself (rejected — pollutes `./data`, breaks fresh-clone semantics); `git clone` of the worktree (rejected — tests committed state only, which inverts TDD ordering); mocking Docker (rejected outright — would assert nothing the spec cares about).

## R10. Caddy check specifics: internal-CA TLS on a substituted `*.localhost` hostname

- **Decision**: The check writes the deploy doc's snippet verbatim with the placeholder hostname substituted to `work-helper.localhost`, mounts it into `caddy:2-alpine` attached to the `work-helper` network, and calls it from two throwaway client containers (each has its own network IP) using `curl --resolve work-helper.localhost:443:<caddy-ip> -k https://work-helper.localhost/...`.
- **Rationale**: "Changed only by substituting the placeholder hostname" is the spec's letter — `work-helper.localhost` keeps that true while Caddy's automatic HTTPS issues an internal-CA certificate for `*.localhost` names instead of attempting ACME against a fake public domain; `-k` accepts the internal CA in the test. Distinct client containers are the only honest way to present distinct source IPs to Caddy for the lockout scenario (all host-originated requests would share one gateway IP).
- **Alternatives considered**: Rewriting the snippet to an `http://` site block for the test (rejected — that edits more than the hostname, breaking the acceptance wording); host-header tricks from a single client (rejected — Caddy would still see one source IP, proving nothing about per-client attribution).

## R11. SPA history fallback: required for US1, implemented behind `serveClient`

- **Decision**: Add a not-found handler active only in `serveClient` mode: GET/HEAD requests whose path does not start with `/api`, `/mcp`, `/oauth`, or `/.well-known` get `index.html` (200); everything else keeps the JSON 404. `buildApp` gains a `clientDir` option (default `dist/client` under cwd) so the integration test can point at a fixture directory instead of requiring a full vite build.
- **Rationale**: The client router uses `createWebHistory`, so a direct browse or refresh at `/people` (US1: "the People page loads") would 404 under `@fastify/static` alone — dev never sees this because Vite's dev server does the fallback. The path prefix list mirrors the server's actual route namespaces (verified against the registered routes).
- **Alternatives considered**: Hash-based router history (rejected — user-visible URL change to dodge a server one-liner); wildcard route instead of not-found handler (rejected — would shadow future routes and fight Fastify's router).

## R12. Deploy doc & placeholder policy

- **Decision**: The deploy doc is `docs/deploy.md`, linked from the README: prerequisites, first deploy (clone → `cp .env.example .env` → edit password → `docker compose up -d --build`), `.env` reference, update procedure (`git pull` → `docker compose up -d --build`), stop/start, logs, the Caddyfile snippet with `work-helper.example.com` placeholder plus the one-time `docker network connect`, and troubleshooting (port conflict → `WORK_HELPER_PORT`; missing password error; malformed config error names the file; `down` network warning while Caddy is attached; config edits vs `git pull`). Placeholder hostname `work-helper.example.com` is used everywhere (FR-012).
- **Rationale**: FR-001/FR-005/FR-009 make the doc itself an acceptance surface — SC-001 is "a reader following only the deploy doc succeeds". Troubleshooting entries map one-to-one to the spec's edge cases.
- **Verification note**: SC-007 ("repo-wide search finds no occurrence of Tyler's real hostname") cannot be a committed automated test without committing the real hostname; the automated check asserts the doc's snippet uses the placeholder, and the verifier/Tyler perform the real-hostname search out-of-repo.
