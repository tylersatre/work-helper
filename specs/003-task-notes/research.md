# Research: Task Notes

**Branch**: `003-task-notes` | **Date**: 2026-08-06

All unknowns flagged during Technical Context drafting, resolved against the existing codebase and the spec's assumptions. No NEEDS CLARIFICATION remain.

## R1. Markdown rendering library & configuration

- **Decision**: markdown-it 14 — the feature's only new dependency (it ships its own TypeScript types). Configured in a single client utility (`src/client/utils/markdown.ts`) from the `'zero'` preset with `html: false`, enabling exactly the rules for the spec's basic set: `heading`, `lheading`, `list`, `emphasis`, `link`, `backticks` (inline code), `code` + `fence` (code blocks), plus the `escape` and `newline` inline plumbing. markdown-it's default `validateLink` stays active (it refuses `javascript:`/`vbscript:`/`data:` URLs, so a hostile link degrades to text). Components render the resulting HTML via `v-html` on a container div.
- **Rationale**: `html: false` makes markdown-it emit raw HTML in note text as *escaped text* — `<script>` arrives in the DOM as literal characters, satisfying FR-009 without a separate sanitizer to configure and keep current. Starting from `'zero'` and enabling rules by name implements FR-008's "exactly the basic set" literally: images, tables, strikethrough, blockquotes, and autolinks are never enabled, so out-of-scope constructs render as ordinary text — the same graceful degradation the spec's malformed-markdown edge case requires, which CommonMark parsing gives for free (a stray `**` is just text). The whole configuration is a pure `string → string` function, unit-testable without mounting a component.
- **Alternatives considered**: marked — rejected: it does not escape raw HTML by itself (its old `sanitize` option was removed), so it requires pairing with DOMPurify — a second dependency and an allowlist to maintain for what markdown-it does with one option. micromark — safe by default too, but restricting it to an exact construct set means assembling a custom extension list; markdown-it's `enable`/`disable`-by-rule-name is the simpler expression of the same intent. A hand-rolled mini-parser for five constructs — rejected: nested emphasis, list continuation, and code-fence edge cases are exactly where hand-rolled parsers leak raw characters, violating SC-005. Vue wrapper packages (`vue-markdown-render` etc.) — rejected: thin layers over markdown-it that add a maintenance surface without adding control.

## R2. Timestamp display: relative label + absolute on hover

- **Decision**: No dependency — a small utility module `src/client/utils/time.ts` with two pure functions. `relativeTime(thenMs, nowMs)`: under 60 s → `"just now"`; under 60 min → `"N minute(s) ago"`; under 24 h → `"N hour(s) ago"`; otherwise → `"N day(s) ago"` (days is the terminal bucket). `absoluteLocal(thenMs, timeZone?)`: `Intl.DateTimeFormat('en-US', { dateStyle: 'medium', timeStyle: 'short', timeZone })` → e.g. `"Aug 4, 2026, 12:00 PM"`; `timeZone` defaults to the browser's and is a parameter only so tests are deterministic. Notes render as `<time :datetime="iso" :title="absoluteLocal(...)">{{ relativeTime(...) }}</time>`, and the notes component keeps a reactive `now` refreshed every 30 s so open views roll over ("just now" → "1 minute ago") without a reload.
- **Rationale**: The spec pins `"just now"` and `"2 days ago"` as testable anchors; `Intl.RelativeTimeFormat` produces `"now"`, not `"just now"`, and would still need the bucket-selection logic — so the built-in buys nothing over ~20 lines of tested code. Storing epoch ms (existing column idiom) makes the stored instant timezone-independent (FR-006); formatting with the browser-default `timeZone` is what converts it to the viewer's local time on hover, and the hard-coded `en-US` locale matches the spec's example copy exactly while keeping unit and browser tests stable across machines. A `title` attribute is the "single hover" of SC-003, is what Playwright can assert directly, and the `<time datetime>` attribute keeps the exact instant machine-readable in the DOM. The 30 s tick bounds label staleness at half the smallest bucket width for a handful of timer wakeups.
- **Alternatives considered**: dayjs or date-fns — rejected: a runtime dependency for two functions the spec pins the copy of anyway. `Intl.RelativeTimeFormat` — rejected as above (wrong copy for the pinned anchors). A per-second ticker — rejected: 60× the wakeups to move a label at most 30 s earlier. Custom tooltip component — rejected: native `title` satisfies "hover reveals" with zero code; a styled tooltip is a visual nicety the spec doesn't ask for.

## R3. Note storage, identity, and ordering

- **Decision**: New `task_notes` table: `id` integer PK autoincrement, `task_id` integer NOT NULL FK → `tasks.id` ON DELETE CASCADE, `text` text NOT NULL, `source` text NOT NULL (`'ui' | 'mcp'`), `created_at` integer NOT NULL (epoch ms). Listing order is `created_at DESC, id DESC` everywhere notes are read. Migration generated by drizzle-kit (`drizzle/0002_*.sql`); FK enforcement is already on via the `PRAGMA foreign_keys = ON` added by feature 002.
- **Rationale**: A real table with per-row ids is required because notes are individually deletable (FR-011) — you can't address one note inside a JSON blob. Epoch-ms integers match the `created_at` idiom of `tasks` and `people` and are inherently UTC instants (FR-006). The `id DESC` tiebreak makes newest-first (FR-005) deterministic even when two notes land in the same millisecond (a plain timestamp sort would order them arbitrarily). CASCADE means a future task-deletion feature can't orphan notes.
- **Alternatives considered**: JSON array column on `tasks` — rejected: no per-note identity for deletion, and every add/delete rewrites the whole blob. ISO-8601 text timestamps — rejected: breaks the integer idiom shared by every other table for no gain (lexicographic and numeric order coincide anyway). An `updated_at` column — rejected: notes are immutable (FR-012); a column implying otherwise is a trap for future code.

## R4. Note text: preservation vs validation

- **Decision**: A note's text is stored **exactly as typed** — no trimming or normalization — whenever its trimmed form is non-empty. Validation (`src/shared/validation.ts`) checks `text.trim().length > 0` without transforming the value. The add-note endpoint rejects trim-empty text with 400 `"Note text is required"` (FR-010); the task-creation form's note field treats trim-empty as *absent* — the task is simply created with zero notes (FR-002), not an error, because the field is optional.
- **Rationale**: The spec's Key Entities define a note's text as "the raw text as typed (markdown source)", and whitespace is semantically load-bearing in markdown — a 4-space-indented line is a code block, trailing double-space is a line break — so the `titleSchema` trim-and-store idiom would silently corrupt note content. Trim-for-validation-only implements the whitespace-only edge case (spaces, tabs, newlines all rejected) while leaving stored bytes untouched. The asymmetry between the two entry points comes straight from the spec: US2-2 makes a blank creation note a normal task creation, while FR-010 makes a blank add-note submission a visible validation failure.
- **Alternatives considered**: Trim then store (the title idiom) — rejected: mutates markdown source. Rejecting a whitespace-only creation-form note with 400 — rejected: the spec calls the field optional and its blank path a success case; treating "   " differently from "" there would surprise for no stated reason.

## R5. Creation-time note: API shape and atomicity

- **Decision**: Extend the existing `POST /api/tasks` body to `{ title, note? }`. When `note` has non-blank trimmed content, `createTask` inserts the task row and its first note row inside one `db.transaction`, with the note's `source: 'ui'` and `created_at` equal to the task's own `createdAt` instant. The response stays the created task (unchanged shape for callers that send no note).
- **Rationale**: One endpoint, one round-trip, one atomic outcome — the form submit either yields a task carrying its first note or nothing, so no failure mode leaves a task silently missing the context Tyler typed (US2-1's detail view "shows one note" is an all-or-nothing promise). Sharing the task's timestamp guarantees the "just now" label in US2-1 and reflects reality: the note was authored at creation. Extending the body keeps `CreateTaskForm.vue` at a single fetch and leaves the no-note path byte-compatible with the existing contract (FR-002).
- **Alternatives considered**: Client chains `POST /api/tasks` then `POST /api/tasks/:id/notes` — rejected: two round-trips with a crash window between them that strands a noteless task, and the client would own transactional semantics that belong to the server. A dedicated `POST /api/tasks-with-note` — rejected: two endpoints for one user action, diverging for no reason.

## R6. Note endpoints & status conventions

- **Decision**: `POST /api/tasks/:id/notes` body `{ text }` → **201** with the created `Note`; **400** `{ error: { message: "Note text is required" } }` on trim-empty text; **404** `"Task not found"` for an unknown task. `DELETE /api/tasks/:id/notes/:noteId` → **204** no body; **404** `"Task not found"` for an unknown task, `"Note not found"` when the note doesn't exist or belongs to a different task. `GET /api/tasks/:id` gains `notes: Note[]` (newest first). No update route exists at all. Error envelope `{ error: { message } }` unchanged.
- **Rationale**: Mirrors the shipped conventions: `POST /api/tasks` returns 201 + the created resource, `DELETE /api/people/:id` returns 204. Notes are self-contained rows — the client prepends the returned note or removes the deleted one locally — unlike person link/unlink, which returns the full `TaskDetail` because link membership and ordering derive from a join the client can't compute. Returning the created note (with server-assigned `id`, `createdAt`, `source`) is also what lets the UI render the authoritative timestamp rather than guessing one. The absence of PATCH/PUT is deliberate and spec-mandated (FR-012): not building an endpoint is the strongest way to guarantee no edit affordance appears.
- **Alternatives considered**: Returning the updated `TaskDetail` from both note endpoints — rejected: resends the people list the operation didn't touch and hides the created note inside a larger payload. 200 + remaining notes on delete — rejected: 204 matches the person-delete precedent and reload scenarios already prove persistence. Idempotent silent delete (200 for a missing note) — rejected: unlike re-unlinking a person (a spec'd no-op), deleting a nonexistent note signals a real client-state bug worth surfacing as 404.

## R7. Delete confirmation mechanism

- **Decision**: Native `window.confirm('Delete this note?')` in the note component; the DELETE request fires only when it returns `true`.
- **Rationale**: FR-011 requires exactly one thing — a prompt standing between click and permanent loss — and `window.confirm` is a true modal with keyboard handling and focus management built in, at zero component state. It is directly testable at both layers the constitution demands: component tests stub it (`vi.spyOn(window, 'confirm')`) to walk the confirm and cancel branches, and the `browser-tester` agent handles the native dialog via Playwright's dialog API. The app has no custom-dialog idiom to stay consistent with (feature 002 shipped person-delete without confirmation), so this sets the simplest possible precedent.
- **Alternatives considered**: Custom modal component — rejected: focus-trap, escape handling, and overlay state to hand-build for no spec'd benefit in an app of native unstyled controls. Two-step inline "click again to confirm" button — rejected: a weaker guard (an accidental double-click deletes) and not obviously a "confirmation prompt" per FR-011/SC-004.

## R8. Source field handling & label mapping

- **Decision**: `source` is a text column typed `'ui' | 'mcp'` at the TypeScript level (Drizzle `text('source', { enum: ['ui', 'mcp'] })`). No API request body ever carries a source: every route sets `'ui'` server-side, and `'mcp'` rows enter only via direct DB inserts in test seeds this slice (per the spec's assumption). The client maps source → label (`'ui'` → "You", `'mcp'` → "via MCP") in exactly one place, in the note component.
- **Rationale**: FR-007 asks this slice to *reserve and display* provenance. Refusing source from request input means there is no spoofing path today, and the future MCP feature will set `'mcp'` from its own server-side tools the same way — no schema or API change needed then, which is the whole point of reserving the column now. Storing the enum token rather than display copy keeps the label a presentation concern: the spec explicitly lets Tyler adjust wording at acceptance, and a single mapping point makes that a one-line change with no data rewrite.
- **Alternatives considered**: A database CHECK constraint on `source` — considered and skipped: the service layer is the column's only writer, so the constraint would guard against code that doesn't exist; the MCP feature can add it if writer count grows. Storing display labels (`"You"`) directly — rejected: copy tweaks would require rewriting rows, and "You" is a viewer-relative word, not a fact about the note. An `author` free-text column — rejected: invents a data shape the spec didn't ask for; the enum is exactly the two provenances the spec names.
