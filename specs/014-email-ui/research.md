# Research: email-ui

**Feature**: 014-email-ui | **Date**: 2026-08-11 | **Spec**: [spec.md](spec.md)

Resolves every decision the spec deferred to `/speckit-plan`: detail-view routing, body sanitization mechanics, test seeding, the backfill's trigger/batching/failure handling, plus the integration choices the codebase exploration surfaced. R# ids are referenced from plan.md, data-model.md, and the contracts.

## R1: Conversation detail is a routed page, not an overlay

- **Decision**: `/emails/:id` as a top-level route alongside a `/emails` list route, both registered in the existing flat router (`src/client/router.ts`); the nav's `activeSection` treats `/emails` and `/emails/...` as Emails, mirroring how `/people/:id` keeps People active (`src/client/App.vue:9-14`).
- **Rationale**: US4 requires link state to survive a page reload and US3 requires click-through from the person record — both are trivial with a URL per conversation and awkward with an overlay. The app's convention is routed pages for primary surfaces (`/tasks/:id`, `/people/:id`); `NModal` is only used for small confirm dialogs. The SPA fallback (`src/server/app.ts:85-104`) already serves `index.html` for `/emails/*`.
- **Alternatives considered**: Overlay/drawer on the list page — rejected: no deep link, reload lands back on the list, and browser evidence would have to re-navigate through the list for every detail scenario.

## R2: HTML bodies — DOMPurify sanitization rendered inside a shadow root

- **Decision**: Add `dompurify` (^3, client-only, bundled types). A `sanitizeEmailHtml()` wrapper (`src/client/utils/sanitize-email.ts`) sanitizes with the default safe HTML profile and an `afterSanitizeAttributes` hook forcing `target="_blank"` + `rel="noopener noreferrer"` on anchors. An `EmailBody.vue` component attaches an **open shadow root** and injects the sanitized markup into it; each message body gets its own shadow root.
- **Rationale**: DOMPurify is the de-facto standard sanitizer and removes scripts, event handlers, and scriptable URLs, satisfying FR-008/SC-003 (formatting renders, nothing executes). The shadow root solves the second real-mail hazard the spec's SC-006 implies: `<style>` blocks in marketing/Outlook mail would otherwise apply globally and can blank or restyle the whole app — inside a shadow boundary they style only their own message. Remote images load as-is per the spec assumption. `target="_blank"` keeps body links from navigating the SPA away mid-read. Playwright pierces open shadow roots, so browser evidence needs no special handling; jsdom supports `attachShadow`, so component tests assert on `shadowRoot` content.
- **Alternatives considered**: Sandboxed `<iframe srcdoc>` — strongest isolation but complicates height sizing, link behavior, and both jsdom and Playwright assertions; overkill when DOMPurify already removes active content. Server-side sanitization (`sanitize-html`) — moves the dependency server-side but sanitizes at a distance from the render, and the raw body would still need to be withheld from the response to be safe. Stripping `<style>` via `FORBID_TAGS` instead of shadow DOM — degrades legitimate formatting and still leaves the app one missed vector away from style bleed.

## R3: Plain-text bodies — escaped interpolation with `white-space: pre-wrap`

- **Decision**: For `bodyContentType === 'text'`, `EmailBody.vue` renders the body as ordinary Vue text interpolation (auto-escaped) inside a block styled `white-space: pre-wrap` — no shadow root, no `v-html`, no linkification.
- **Rationale**: Matches the clarification exactly: escaped text, line breaks and blank-line paragraphs preserved (`pre-wrap` preserves both), URLs stay plain text. Vue escaping makes injection structurally impossible for the text path.
- **Alternatives considered**: Splitting into `<p>` per blank line — extra code for identical visual output. Auto-linking URLs — explicitly ruled out by the clarification.

## R4: Schema delta — `is_inline` column plus an `app_state` marker table, one additive migration

- **Decision**: `email_attachments.is_inline` integer boolean NOT NULL DEFAULT 0, and a new `app_state` table (`key` text PK, `value` text NOT NULL) whose first use is the backfill completion marker. One generated migration `drizzle/0001_*.sql` containing only `ALTER TABLE ... ADD COLUMN` and `CREATE TABLE` — verified to not recreate any table.
- **Rationale**: `DEFAULT 0` (non-inline) implements the spec's fail-open rule — anything the backfill can't classify keeps showing as a real attachment. SQLite's `ADD COLUMN` is metadata-only, so the deployed production rows are untouched (constitution Data & migrations); this is deliberately the first additive migration on top of the immutable `0000_futuristic_sunspot` baseline. A generic key-value `app_state` table beats a bespoke one-column table because it is the pattern future one-time markers will need too.
- **Alternatives considered**: Deriving "backfill done" without a marker — impossible: all-zero flags is also the legitimate pre-backfill state. Storing the marker in a file — the DB is the single source of truth for data state and travels with backups. A `backfill_runs` history table — over-modeled for a one-time job whose only queryable fact is doneness.

## R5: Ingestion records `isInline` through the provider contract

- **Decision**: `MailAttachmentMeta` gains `isInline: boolean`. `GraphMailProvider.fetchAttachmentMetadata` adds `isInline` to its `$select` and maps it (absent → `false`). `FakeMailProvider`'s `SeedAttachment` gains optional `isInline` (default `false`). `sync.ts` writes the flag on both the new-message insert and the refresh delete+reinsert paths, so refreshed messages self-heal without the backfill.
- **Rationale**: Graph's `attachment.isInline` is exactly the fact the spec needs and is already available on the endpoint the sync calls — one `$select` field, no extra requests. Flowing it through the provider interface keeps `FakeMailProvider` faithful, which is what makes TDD and browser-evidence seeding honest (spec: 012 research R3 explicitly recorded ignoring inline; this reverses that with data preserved).
- **Alternatives considered**: Inferring inline-ness from `contentId`/content-type heuristics — Graph provides the authoritative flag; heuristics would misclassify.

## R6: MCP tools stay behaviorally identical — filtering is opt-in per call site

- **Decision**: `queries.ts` helpers gain optional parameters with behavior-preserving defaults: `listConversations` gets `attachmentRollup: 'all' | 'non-inline'` (default `'all'`), `getConversation` gets `{ attachments: 'all' | 'non-inline', includeOriginalBody?: boolean }` (defaults `'all'`, `false` — `bodyOriginal`/`bodyContentType` are added to `ConversationMessage` as optional fields populated only on request). Only the new REST routes pass the non-default options; MCP call sites in `src/server/mcp/tools.ts` are untouched. Extended regression tests in `email-read-tools.test.ts` pin MCP output on a store containing inline attachments.
- **Rationale**: FR-018 forbids changing MCP tools, and the clarification scopes inline-exclusion to "email views". Filtering inside the shared helpers unconditionally would silently change `hasAttachments` and attachment lists for MCP consumers; option parameters with defaults keep one query implementation while making the UI-only behavior explicit and the MCP invariance testable.
- **Alternatives considered**: Duplicate UI-specific query functions — drift risk between two copies of non-trivial SQL. Filtering in the route layer after fetching — works for attachment lists but cannot fix the `hasAttachments` rollup, which is computed in SQL.

## R7: REST surface — three new GET endpoints; both writes reuse existing endpoints

- **Decision**: New `src/server/routes/emails.ts` with `GET /api/emails/conversations` (query `limit` default 25, `cursor`; returns `{ conversations, nextCursor }` via the existing keyset cursor), `GET /api/emails/conversations/:id` (full detail incl. `bodyOriginal`/`bodyContentType`, non-inline attachments, participants with person links; 404 when absent), and `GET /api/people/:personId/email-conversations` (person's conversations with address+role rollups; 404 when the person is absent). No new write endpoints: the link control calls the existing `POST /api/people/:personId/emails { value }` (whose `addEntry` service links an existing unlinked address row, `contact-entries.ts:81-113`), and the create-person control submits the existing `POST /api/people` (whose `createPerson` links a pre-existing unlinked synced address, `people.ts:114-122`). The link control's person search reuses `GET /api/people?q=` unchanged.
- **Rationale**: The email read queries already exist server-side for MCP — the feature's server work is exposing them over HTTP, not rewriting them. FR-014 *requires* the shared email-address rules from email-sync, and those rules live in exactly the two services the existing endpoints call — reusing them makes divergence impossible and inherits the 409 conflict behavior the edge case demands. The person-section path is `email-conversations` (not `.../emails`) because `POST /api/people/:personId/emails` already means "add an email address contact entry" — overloading GET on that path would give one URL two unrelated meanings.
- **Alternatives considered**: A dedicated `POST /api/email-addresses/:id/link` — a second code path into linking rules that FR-014 says must be shared; rejected. Numbered-page pagination — the codebase's established paging is keyset cursors, which are stable while newest-first mail arrives.
- **Documented nuance**: the spec's assumption pins the search to "the existing task-linking widget's behavior"; that widget's server search (`listPeople`, `people.ts:148-152`) matches first name, last name, and the **primary** email only. Reusing it unchanged is the spec-mandated choice; the acceptance scenarios only exercise name matches.

## R8: Person email section — a new conversation-grouped query, all rows returned, client slices 5/show-all

- **Decision**: New `conversationsForPerson(db, personId)` in `queries.ts`: conversations having at least one participant whose address's `person_id` matches, newest `latestMessageAt` first, each with `{ conversationId, subject, latestMessageAt, addresses: [{ address, roles: [...] }] }` where `addresses` is the person's distinct involved addresses and `roles` each address's distinct roles across the conversation's messages. The endpoint returns all rows; the client renders 5 and reveals the rest with an in-place show-all.
- **Rationale**: The existing `emailsForPerson` is per-message (built for the MCP tool) — FR-015's row shape is per-conversation with a roles rollup, a different aggregation, so a new helper is honest rather than a lossy re-grouping in the route. One person's conversation count is small at personal scale, so no server paging; returning everything makes show-all a pure client reveal, exactly matching the clarification ("every distinct involved address, each with all of its distinct roles").
- **Alternatives considered**: Reusing `emailsForPerson` and grouping client-side — pushes aggregation into the UI and still fetches per-message rows page by page. Server-side 5-plus-cursor — spec explicitly caps the section at one show-all, no pagination.

## R9: Backfill — opportunistic, sequential, resumable; marker written only on completion

- **Decision**: New `attachment-backfill.ts` service with a single-flight guard. **Triggers**: (a) fire-and-forget after server listen, (b) after every successful sync run (from `SyncCoordinator`), until done. **Algorithm**: if the `app_state` marker exists → no-op; select distinct stored messages that have attachment rows; if none → write the marker immediately (fresh DBs are done by definition — ingestion now records the flag); else per message, sequentially: `fetchAttachmentMetadata(graphMessageId, { allowNotFound: true })`; `null` (message gone from mailbox) → skip permanently; otherwise match each stored attachment row to fetched metadata by `(name, sizeBytes)` and `UPDATE email_attachments SET is_inline = ?` for matches — unmatched rows stay untouched (non-inline). Marker written only when every candidate message was fetched or permanently skipped. **Failure handling**: `MailboxNotConnectedError` or any transport/HTTP error aborts the run silently (logged); no marker; the next trigger retries from the top — safe because the job is idempotent and only writes flags.
- **Rationale**: The startup trigger gives immediate effect on deploy (the MSAL token cache persists in `./data/mail-token-cache.json`, so a silent token is normally available); the after-sync trigger is the guaranteed-connected retry path when it isn't. Sequential calls match the codebase's existing style (sync already does one attachment fetch per message with no batching/429 handling) and personal-scale volumes. Matching by `(name, sizeBytes)` is the only join available — stored rows carry no Graph attachment id — and ambiguity is harmless because identical name+size duplicates get the same flag. Message-gone → skip implements the spec's fail-open edge case verbatim. FR-019's "modifies only the inline flag" is enforced structurally: the service contains no insert or delete.
- **Alternatives considered**: Manual `scripts/` CLI trigger — leaves production unfiltered until Tyler remembers to run it. Per-message progress bookkeeping — a full re-run costs a handful of metadata GETs at this scale; a resumability table is over-engineering. Recording runs in `sync_runs` — that table's contract is one row per user-triggered sync; polluting it misrepresents both.
- **Provider change this requires**: `fetchAttachmentMetadata(messageId, options?: { allowNotFound?: boolean })` returning `MailAttachmentMeta[] | null` — `null` only under `allowNotFound` on 404, via the `authorizedFetch` option that already exists (`graph-provider.ts:120`); the sync call site keeps today's throwing behavior.

## R10: Test seeding — everything flows through `FakeMailProvider` and a real sync

- **Decision**: Integration tests keep the established pattern: inline `SeedMessage[]` → `FakeMailProvider` → `buildApp` → trigger a sync → assert over `app.inject`. Browser evidence extends `dev-seed.ts` into a scenario-rich mailbox (the US1 pair "Pricing question"/"Quote attached" with exact metadata, 30 conversations for load-more, the script-bearing HTML body, an inline-only-attachment message, unmatched addresses for US4, a second address for Sam Rivera for US3) served by `MAIL_PROVIDER=fake`; the evidence run captures the empty state on the fresh DB first, then triggers a sync from the Sync page UI and browses. People (Sam Rivera, Ana Alvarez) are created through the People page during evidence, since sync never creates people. Component tests stub `fetch` per convention.
- **Rationale**: Seeding through the real ingestion path is the only seeding that proves the store the UI reads is the store sync actually writes — including the new `isInline` recording — and it reuses infrastructure that already exists for exactly this purpose (`dev-seed.ts` says so in its header comment). Direct DB inserts would bypass `findOrCreateAddressId`, participant snapshots, and the attachment write path, letting fixtures drift from production shapes.
- **Alternatives considered**: A drizzle seed script inserting rows directly — faster to write, but tests would pass against data ingestion can't produce. Seeding via MCP — MCP has no write tools for mail by design.

## R11: Shared response types live in `src/shared/types.ts`

- **Decision**: The three REST response shapes (`EmailConversationSummary`, `EmailConversationDetail` + its message/participant/attachment parts, `PersonEmailConversation`) are declared in `src/shared/types.ts`; the routes map `queries.ts` results onto them and the client imports them.
- **Rationale**: That is the repo's convention for every client-consumed API shape (`Person`, `TaskDetail`, `Tag`…); the email types' current home in `queries.ts` predates any HTTP surface. Mapping at the route keeps the server-internal query types free to carry extra fields (e.g. `isInline`) that the wire shape excludes.
- **Alternatives considered**: Client `import type` from `src/server/...` — works mechanically (types erase) but crosses the layering boundary every other page respects.

## R12: UI composition follows existing app conventions

- **Decision**: Hand-rolled list rows in the app's shared row style (not `n-data-table`), `NEmpty` empty states with `data-testid` (`emails-empty`, `person-emails-empty`), `<p role="alert">` error text, dates via the existing `absoluteLocal` helper, unread shown as a dot/badge plus bold row text and attachment as a paperclip glyph with an accessible label, load-more and show-all as plain `NButton`s. "(no subject)" renders as a styled muted placeholder via a shared helper wherever subjects appear (FR-003). The create-person control expands `PersonForm` (create mode, `initialValues` prefilled from the display-name split and address) inline under the address, matching the app's inline-form convention — not a modal; the link control reuses the `LinkedPeople.vue` search pattern (300 ms debounce over `GET /api/people?q=`, result rows "First Last — email", `data-testid="search-result"`). Prefill split: two-word display name → first/last; anything else → both name fields blank (FR-013), implemented as a pure util with unit tests.
- **Rationale**: Every choice mirrors an existing site in the codebase (rows: `SyncPage`/`TagsPage`; empty: `PeoplePage`; search: `LinkedPeople`; inline form: `PeoplePage`+`PersonForm`, which already supports `initialValues` and renders the email field in create mode) — no new UI vocabulary to test or maintain.
- **Alternatives considered**: `NModal` for the create form — the app only uses modals for confirms, and an inline expansion keeps the conversation context visible while linking.
