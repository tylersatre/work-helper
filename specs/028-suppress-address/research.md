# Phase 0 Research: Suppress Address

No `NEEDS CLARIFICATION` markers were left in the Technical Context — the codebase already has direct precedent for every piece of this feature (unlinked-address query logic, the two existing "link an unlinked address to a person" write sites, MCP tool registration, idempotent-insert patterns). The research below documents the concrete decisions made while reconciling the spec against `src/server/services/email/queries.ts`, `src/server/services/contact-entries.ts`, `src/server/services/people.ts`, and `src/server/mcp/tools.ts`.

## R1: A new `suppressed_addresses` table, keyed to `email_addresses.id`

- **Decision**: Add one new table, `suppressedAddresses`, with `id` (PK), `addressId` (FK → `emailAddresses.id`, unique, `onDelete: 'cascade'`), and `suppressedAt` (integer, not null). One new additive migration (`CREATE TABLE` + its unique index), consistent with every migration shipped so far.
- **Rationale**: `email_addresses.personId IS NULL` already is the "unlinked" predicate (`listUnlinkedAddresses` in `queries.ts`). Suppression is a boolean flag scoped to one address record, not a new kind of entity with its own identity — a join-shaped table keyed by `addressId` mirrors `personTags`/`taskTags`'s existing join-table style (composite/simple FK + `onDelete: cascade`) more closely than inventing a denormalized `suppressed_addresses.value` column that would need its own case-insensitive uniqueness logic duplicating `email_addresses_value_unique`. Every suppressible address (per R2) is, by construction, referenced by at least one `email_participants` or `calendar_event_participants` row, which is exactly the condition `isEmailAddressReferenced` (in `contact-entries.ts`) already uses to guarantee `removeEntry` never hard-deletes it — so `addressId`'s FK will never dangle in practice, but `onDelete: cascade` is still the safe, standard choice for the FK.
- **Alternatives considered**: A denormalized `suppressed_addresses.value text unique` table with no FK — rejected because it would need to duplicate `email_addresses`'s `lower(value)` uniqueness/matching logic and wouldn't benefit from `onDelete: cascade` safety, for no upside (nothing needs to suppress an address that has no `email_addresses` row, per R2). A boolean `is_suppressed` + `suppressed_at` column pair added directly to `email_addresses` — rejected: it works for the flag itself but FR-005's "list every suppressed address, most-recent first" would need a `WHERE is_suppressed = 1 ORDER BY suppressed_at DESC` scan of the whole table anyway, and a separate table keeps this single-purpose, low-cardinality flag out of the hot `email_addresses` row (which is read on every send/receive) and out of `email_addresses`'s existing snapshot/migration history, which the constitution says to treat conservatively once shipped.

## R2: "Has this address ever appeared in synced mail" reuses `list-unlinked-addresses`'s own qualifying predicate, scoped to one address

- **Decision**: `suppress-address`'s validation that an address is a legitimate suppression target is: (a) an `email_addresses` row exists for that value (case-insensitive), and (b) that row's `personId IS NULL`. Given the schema, condition (a) is sufficient by itself to guarantee the address participates in at least one synced message or calendar event — see rationale — so no separate "does it qualify" query against `email_participants`/`calendar_event_participants` is needed beyond the existing `findEmailAddressByValue` lookup already used by `contact-entries.ts`/`people.ts`.
- **Rationale**: Walking every write path that can create an `email_addresses` row: (1) email/calendar sync creates a row with `personId: null` only when it encounters the address as a message or event participant (the only path that ever produces an unlinked row); (2) `addEntry`/`createPerson` insert a row only with a non-null `personId` supplied by the caller (adding an address always requires a target person — there is no "add an address to nobody" call). So the *only* way an `email_addresses` row can have `personId IS NULL` is via sync having seen it participate in a message or event. This means "exists in `email_addresses` with `personId IS NULL`" and "has appeared in synced mail/calendar data and is currently unlinked" are the same condition — re-deriving it from `email_participants`/`calendar_event_participants` directly would be redundant. FR-002's "never appeared in any synced message" is satisfied by rejecting when no row exists at all (`never-seen@example.com` in the spec's own edge case never got an `email_addresses` row in the first place).
- **Alternatives considered**: Re-running `listUnlinkedAddresses`'s full qualifying CTE (mail-OR-non-resource-event) scoped to one address, to also reject a hypothetical row that exists only via a `resource`-role calendar participant (e.g. a synced meeting room) and so would never actually surface in `list-unlinked-addresses`'s output. Rejected for this slice: no sync path in this codebase creates a standalone `email_addresses` row for a `resource`-only participant that isn't also reachable another way (rooms/equipment addresses are calendar-only participants, but nothing here restricts them from also existing in `email_addresses`, and the spec's own edge cases and acceptance scenarios never exercise this case). Revisit only if evidence surfaces such a row in practice — flagged, not built, per YAGNI.

## R3: New service module `src/server/services/address-suppression.ts`; `tools.ts` stays a thin wrapper

- **Decision**: Add `src/server/services/address-suppression.ts` exporting `suppressAddress(db, rawAddress)`, `unsuppressAddress(db, rawAddress)`, `listSuppressedAddresses(db)`, and an internal `clearSuppressionForAddressId(db, addressId)` helper used by R4's auto-clear hook. `tools.ts` registers three thin tools that call these and map results to `toolError`/`structuredContent`, matching every other tool in the file.
- **Rationale**: Matches the established split (`src/server/services/*` owns queries/mutations/validation; `tools.ts` owns MCP shape + error-message mapping) documented across `people.ts`, `contact-entries.ts`, and `tags.ts`. Suppression has no REST/UI surface in this slice (spec Assumptions), so unlike `contact-entries.ts`/`tags.ts` it won't be dual-consumed by a route — but it still belongs in the services layer for symmetry, testability without the MCP transport, and because `clearSuppressionForAddressId` must be called *from* `people.ts` and `contact-entries.ts` (R4), which would be circular if suppression logic lived inside `tools.ts`.
- **Alternatives considered**: Folding suppress/unsuppress/list into `contact-entries.ts` alongside `addEntry`/`removeEntry` — rejected: that file is scoped to per-person contact-entry CRUD (every exported function takes a `personId`), and suppression is deliberately about addresses with *no* person; a separate module keeps the "no person in scope" nature of this feature clear and avoids growing an already-large file with an unrelated concern.

## R4: Auto-clear-on-link hooks into the two existing "link an unlinked address" write sites

- **Decision**: Inside the same `db.transaction`, immediately after each of the two places that flip an existing unlinked `email_addresses` row's `personId` from `null` to a person id, add `tx.delete(suppressedAddresses).where(eq(suppressedAddresses.addressId, existing.id)).run()` (harmless no-op if no suppression row exists):
  - `contact-entries.ts::addEntry`, the `existing.personId === null` branch (currently lines ~115–121).
  - `people.ts::createPerson`, the `existingEmail` truthy branch (currently line ~133).
- **Rationale**: These are the *only* two places in the codebase that transition an `email_addresses` row from unlinked to linked (confirmed by reading every write to `emailAddresses.personId` across `people.ts`, `contact-entries.ts`, and the calendar/email sync services, which only ever write `personId: null` for new rows, never promote one). Deleting inside the same transaction makes the clear atomic with the link (FR-009's "as part of the same operation") — no separate unsuppress call, and no window where a suppressed-but-now-linked address is briefly visible as suppressed.
- **Alternatives considered**: A `personId`-write trigger at the DB level (SQLite `AFTER UPDATE` trigger) — rejected as inconsistent with this codebase's style (no triggers exist anywhere in `schema.ts`/`drizzle/`; all such invariants are enforced in the TypeScript service layer) and harder to test/reason about than two explicit, already-transactional call sites.

## R5: `list-unlinked-addresses` gains a `NOT EXISTS` filter against `suppressed_addresses`

- **Decision**: Add `AND NOT EXISTS (SELECT 1 FROM suppressed_addresses sa WHERE sa.address_id = ea.id)` to the qualifying/final `SELECT` in `listUnlinkedAddresses` (`queries.ts`), scoped so a suppressed address is excluded regardless of which branch of the `qualifying` CTE it came from (mail-only, event-only, or both).
- **Rationale**: FR-008 is a straightforward filter addition to an existing, already-parameterless, always-live query — no caching/materialization to invalidate, no other caller of this function to consider (grep confirms `listUnlinkedAddresses` has exactly one call site, the `list-unlinked-addresses` MCP tool). The function's own doc comment already flags this as anticipated ("complete, unsuppressed, and computed live" — R11 from the original `mcp-people-tools` research) and will need a small wording update once suppression exists.
- **Alternatives considered**: Filtering suppressed addresses out in `tools.ts` after calling `listUnlinkedAddresses` — rejected: would require loading every suppressed address into memory and cross-referencing per call for no benefit over pushing the exclusion into the SQL, and would leave the exported `listUnlinkedAddresses` function itself still (incorrectly) claiming to return "every" unlinked address for any other future caller.

## R6: `suppress-address` idempotency reuses the `onConflictDoNothing()` pattern; `unsuppress-address` reuses plain-delete-is-idempotent

- **Decision**: `suppressAddress` inserts via `db.insert(suppressedAddresses).values({ addressId, suppressedAt: Date.now() }).onConflictDoNothing()` against the unique index on `addressId` — a second suppress call for an already-suppressed address is a true no-op at the DB level, leaving `suppressedAt` untouched (FR-004), with zero read-then-write race window. `unsuppressAddress` does a plain `db.delete(suppressedAddresses).where(eq(suppressedAddresses.addressId, addressId)).run()` — deleting a row that doesn't exist is already a no-op in SQL, satisfying FR-007 with no extra branching.
- **Rationale**: Direct precedent — `attach-tag`'s `attachExistingTagToPerson`/`attachExistingTagToTask` (`tags.ts`) already use `onConflictDoNothing()` for exactly this "second call is a harmless no-op, first call's data wins" shape, cited by name in the spec's own Assumptions section as the model for this feature's idempotency.
- **Alternatives considered**: Read-then-conditionally-insert (`SELECT` for existing row, only `INSERT` if absent) — rejected as an unnecessary extra round trip and a (tiny) TOCTOU race that `onConflictDoNothing()` avoids for free.

## R7: Address input validation — a plain trimmed non-empty string, not `entryValueSchema`

- **Decision**: `suppress-address`/`unsuppress-address`'s `address` input is validated with a small local schema (`z.string().trim().min(1, 'An address is required')`), not the existing `entryValueSchema` from `src/shared/validation.ts`.
- **Rationale**: `entryValueSchema` is shared across both email and phone contact entries and is used when *creating* a new entry, where format strictness (rejecting a garbage string before it ever reaches the DB) matters because there's no existing record to fall back on. Here, the address is being matched against an already-synced `email_addresses` row — a malformed string simply won't match anything and falls through to the existing "never appeared in synced mail" error (FR-002), which is the correct, spec-mandated outcome regardless of *why* it didn't match. Reusing `entryValueSchema` would risk rejecting a syntactically-unusual-but-real synced address (e.g. one Microsoft Graph delivered with a quirk) with the wrong error message ("invalid format" instead of "never appeared").
- **Alternatives considered**: Reusing `entryValueSchema` for consistency — rejected per the rationale above; the two validations serve different purposes (gatekeeping new data vs. looking up existing data) despite superficially sharing a "string" type.

## R8: Case-insensitive matching reuses `findEmailAddressByValue`

- **Decision**: All three tools resolve their `address` input via the existing exported `findEmailAddressByValue(db, value)` (`contact-entries.ts`, `lower(${emailAddresses.value}) = lower(${value})`), the same function `addEntry`/`createPerson` already use.
- **Rationale**: FR-011 requires case-insensitive matching "consistent with address matching elsewhere in `mcp-people-tools`" — `findEmailAddressByValue` *is* that existing matching logic, already exported and unit-tested indirectly via `contact-entries.test.ts`/`people.test.ts`. No new comparison logic needed.
- **Alternatives considered**: None — reusing an existing, already-correct, already-exported function is strictly simpler than writing a parallel comparison.

## R9: Output shape returns the address in its stored (synced) casing, not the caller's input casing

- **Decision**: `suppress-address`, `unsuppress-address`, and `list-suppressed-addresses` all return the `email_addresses.value` string as stored (the casing Microsoft Graph originally delivered), not whatever casing the caller passed to `suppress-address`/`unsuppress-address`.
- **Rationale**: Matches `listUnlinkedAddresses`'s existing behavior (`ea.value AS address` — stored casing) and avoids a confusing mismatch where suppressing `NEWS@Example.com` makes `list-suppressed-addresses` show a different casing than `list-unlinked-addresses` showed for the same underlying row.
- **Alternatives considered**: Echoing the caller's input casing back — rejected as inconsistent with every other address-returning tool in this codebase.

## R10: Auth — no new code needed

- **Decision**: Register all three tools through the same `createMcpServer(context)` factory already gated end-to-end by `src/server/mcp/routes.ts`'s bearer-token check (which runs before `createMcpServer` is even invoked) and the `mcp-authentik-auth` OAuth flow that mints that token.
- **Rationale**: Confirmed by reading `routes.ts` — authorization is enforced once at the transport layer, not per-tool. FR-013 is satisfied by construction, exactly like every prior MCP-tools feature (`mcp-move-tasks`, `mcp-people-tools`, `mcp-note-tag-task-tools`).
- **Alternatives considered**: None needed — same as R10 in the `026-note-tag-task-tools` plan this mirrors.

## R11: Schema change ships as a new numbered migration at implementation time, not during planning

- **Decision**: This plan documents the `suppressedAddresses` table shape (R1, `data-model.md`) but does not edit `src/server/db/schema.ts` or run `npx drizzle-kit generate` — that happens under TDD during `/speckit-implement`, per the project's stated workflow (`CLAUDE.md`: "Schema changes are made by editing `src/server/db/schema.ts` and generating a new numbered migration").
- **Rationale**: Consistent with how every other schema-changing feature in this repo (e.g. `018-companies`, `019-calendar-sync`) sequenced its migration — planning documents the shape, implementation writes the migration next to its first failing test. The new table is purely additive (`CREATE TABLE` + one unique index), so no data-loss risk and no lossy-migration disclosure is needed per the constitution's migration section.
- **Alternatives considered**: None — this is procedural, not a design choice.
