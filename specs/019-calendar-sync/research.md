# Phase 0 Research: Calendar Sync

All `/speckit-plan` decisions deferred by the spec (spec.md Assumptions, brief Open questions) are resolved here. Codebase facts below were verified against the worktree at planning time.

## R1: Graph endpoint — `calendarView` with server-computed UTC window

**Decision**: Fetch events with `GET https://graph.microsoft.com/v1.0/me/calendarView?startDateTime={startUtc}&endDateTime={endUtc}` with `$select` for the stored field set, `$orderby=start/dateTime`, `$top=100`, following `@odata.nextLink` for pagination — the same paging loop as `GraphMailProvider.fetchMessages` (`src/server/services/email/graph-provider.ts:150-159`). The window comes from the existing `computeSyncWindow` (`src/server/services/email/sync.ts:30-42`): inclusive local midnight of `startDate` to exclusive local midnight of `endDate + 1`, exactly email sync's server-local inclusive-endpoints convention (FR-007).

**Rationale**: `calendarView` does three spec-critical things natively: it targets the default calendar (`/me/calendarView` — FR-007's "default calendar" for free, secondary calendars naturally excluded), it returns events whose span **overlaps** the window (the spec's all-day/multi-day overlap rule, FR-012 and the edge cases, without client-side span math at fetch time), and it **expands recurring series into individual occurrences**, each with its own `id` and dates plus a shared `seriesMasterId` — precisely FR-009's storage model. Reusing `computeSyncWindow` keeps email and calendar range semantics provably identical and its validation errors ("A start date and end date are required", "Start date must not be after end date") already match the spec's required messages.

**Alternatives considered**: `GET /me/events` returns series masters (one row per series, a recurrence rule, no occurrences) — would force us to expand recurrences ourselves; rejected. Graph delta queries (`/calendarView/delta`) support incremental sync but complicate the on-demand any-range model and add sync-token state the spec doesn't want (no watermark; rolling prefill); rejected for this slice.

## R2: Event identity — immutable Graph event id, unique per occurrence

**Decision**: Store the Graph event `id` as `calendar_events.graph_event_id` with a case-sensitive unique index, and upsert on it. Requests send `Prefer: IdType="ImmutableId"`, which `authorizedFetch` (`graph-provider.ts:121-148`) already attaches for mail and which applies to events too. `seriesMasterId` is stored as the spec's "series identifier" (`series_master_id`, null for one-off events).

**Rationale**: Immutable ids don't change when items move, so identity is stable across re-syncs (FR-010's no-duplicates guarantee — the same mechanism email uses via `email_messages.graph_message_id`). Expanded occurrences each get their own id derived from the series master plus the original start date, so per-occurrence upsert works; an individually modified occurrence (exception) keeps its id and `seriesMasterId`, satisfying the moved-occurrence edge case.

**Alternatives considered**: `iCalUId` is shared across all occurrences of a series, so it cannot key occurrences; rejected. A composite key (subject + start) breaks the moment an event is renamed or moved; rejected.

## R3: Times — request UTC, store epoch milliseconds, tools return epoch milliseconds

**Decision**: Send `Prefer: outlook.timezone="UTC"` so Graph returns `start`/`end` as `{ dateTime, timeZone: "UTC" }`; parse `dateTime + 'Z'` to epoch ms and store `start_at` / `end_at` as integers. MCP tools return `startAt` / `endAt` as epoch-ms numbers — resolving the spec's deferred "exact representation of event times in tool responses". Sync/list inputs remain `YYYY-MM-DD` strings interpreted as inclusive server-local days.

**Rationale**: Every timestamp in the schema and every MCP tool response is already an epoch-ms integer (`sent_at`, `ran_at`, `lastMessageAt`…) — a new representation would be gratuitous inconsistency. UTC parsing is trivial and dependency-free; interpreting arbitrary Windows/IANA timezone names from Graph would need a tz library for zero spec benefit.

**All-day caveat (recorded, accepted)**: Graph stores all-day events as midnight-to-midnight in their creation timezone; converted to UTC those instants may not be midnights. We store the flag (`is_all_day`) plus the span exactly as returned; overlap-based range queries remain correct either way, and the acceptance tests run against the seeded fake provider where the span is controlled. If Tyler's real-calendar pass surfaces a shifted-looking all-day date, that is a rendering concern for the future `calendar-ui` feature, not a storage defect in this slice.

## R4: Scope extension — add `Calendars.Read` to the single SCOPES constant

**Decision**: Change `src/server/services/email/graph-auth.ts:5` to `const SCOPES = ['Mail.Read', 'Calendars.Read', 'offline_access']`. No other auth code changes.

**Rationale**: That one constant feeds all three flows — `getAccessToken` (used by both providers), `verifyConnection`, and `beginSignIn` — so extending it extends the whole connection uniformly. For the already-connected production mailbox, the cached consent doesn't cover the new scope, so `acquireTokenSilent` will fail and surface the existing `MailboxNotConnectedError('expired')` path: the Sync page shows the established reconnect guidance and Tyler reconnects once via the device-code flow, consenting to the widened set. This is exactly the one-time reconnect the spec's Assumptions predict, and it reuses the disconnected-mailbox error surface (FR-013) with zero new code. If the Azure app registration uses static consent, `Calendars.Read` (delegated) must be added there before the reconnect — noted in quickstart.md for the acceptance pass.

**Alternatives considered**: A second scope set / second token acquisition just for calendar would double the auth surface and still require re-consent; rejected. Incremental consent via a separate interactive flow adds UI for no benefit over one reconnect; rejected.

## R5: Provider abstraction — `CalendarProvider` mirroring `MailProvider`, fake for tests and dev

**Decision**: New `src/server/services/calendar/provider.ts` defines `CalendarProvider { fetchEvents(window: CalendarWindow): AsyncIterable<ProviderCalendarEvent[]> }` plus the provider-level event type (subject, start/end, isAllDay, isCancelled, location, body, organizer, attendees with type and response, online-meeting URL, categories, webLink, id, seriesMasterId). `GraphCalendarProvider` implements it against `calendarView` with the injected `getAccessToken` (same injection as `GraphMailProvider`, wired in `src/server/index.ts`); `FakeCalendarProvider` is seedable from `SeedEvent[]` with the same failure injection knobs as `FakeMailProvider` (`failImmediately`, `throwAfterEventCount`) and reimplements the overlap-window and paging semantics. When `MAIL_PROVIDER=fake`, the calendar provider is the fake too, seeded from a new `dev-seed.ts` — this resolves the spec's deferred "simulated calendar seeded by test setup" mechanism: integration tests inject `FakeCalendarProvider` into `buildApp`, unit tests stub `fetch` against `GraphCalendarProvider`, and the browser-tester runs the dev server with the fake seed.

**Rationale**: This is a straight copy of the proven email test architecture (`fake-provider.ts` as the dominant strategy, `fetch`-stub unit tests for the real Graph client, MSAL untouched) — every sync acceptance scenario becomes seedable and deterministic. Tying fake selection to the existing `MAIL_PROVIDER` env matches the product reality that mail and calendar share one connection.

**Alternatives considered**: A mock HTTP Graph server — the repo has none and the injected-fake pattern is established; rejected. Recording real Graph fixtures — brittle, unseedable per-test; rejected.

## R6: Run history — new `calendar_sync_runs` table, not a discriminator column

**Decision**: A new `calendar_sync_runs` table mirroring `sync_runs` column-for-column (`ran_at`, `start_date`, `end_date`, `source` web|mcp, `status` success|failure, `new_count`, `updated_count`, `error`), with its own newest-first list query and `GET/POST /api/calendar-sync/runs` routes.

**Rationale**: The spec treats the calendar run history as its own history with identical shape (FR-005), and nothing ever queries email and calendar runs together. A `kind` column on `sync_runs` would work, but it silently changes the meaning of every existing email query and endpoint — `GET /api/email-sync/runs` returns all rows today and feeds the email prefill from "newest successful run", so an unfiltered query would corrupt email prefill with calendar rows. A separate table makes that class of regression structurally impossible, keeps the migration purely `CREATE TABLE` (safest possible under the production-data rule), and costs one small parallel schema block.

**Alternatives considered**: `ALTER TABLE sync_runs ADD COLUMN kind DEFAULT 'email'` — data-safe and normalized, but every existing email-run query must gain a `WHERE kind = 'email'` filter and a missed one is a silent cross-contamination bug; rejected on risk, not feasibility.

## R7: Global single-flight — extend the existing `SyncCoordinator` instance

**Decision**: The one `SyncCoordinator` instance decorated on the app (`src/server/app.ts:76`) keeps its private `running` boolean and gains `triggerCalendar(...)` (running the calendar sync engine and recording into `calendar_sync_runs`) plus an `isRunning()` accessor. Both email and calendar triggers, from both web routes and MCP tools, check and set the same flag.

**Rationale**: FR-006 demands one sync at a time globally across kinds and entry points; the existing guard already spans entry points because the instance is shared — extending the same instance to a second kind makes the global guarantee a property of the object graph rather than of discipline. Validation stays in the callers (as today, deliberately — `sync-coordinator.ts:36-41`) so rejected calls record no history row (FR-018).

**Alternatives considered**: A second coordinator with a shared mutex module — two objects that must agree instead of one that can't disagree; rejected. A DB-level lock — the app is single-process (one Docker container), so an in-process flag is already correct; rejected as needless.

## R8: In-progress visibility — `GET /api/sync/status` polled by the Sync page

**Decision**: New endpoint `GET /api/sync/status` → `{ running: boolean }` backed by `SyncCoordinator.isRunning()`. The Sync page polls it every 3 seconds (the `MailboxPanel` polling pattern, `src/client/components/MailboxPanel.vue:14,31-64`) and disables **both** Sync buttons while `running` is true; each section additionally disables both buttons immediately on its own submit (local state), and the 409 remains the hard server-side guard.

**Rationale**: US1 scenario 3 requires the web buttons to be disabled while *any* sync runs, including one an agent started over MCP — today nothing exposes that state (the email button's `syncing` ref is local-only and the 409 is the only signal). A tiny boolean endpoint plus the established polling idiom is the smallest mechanism that makes the criterion true and browser-testable.

**Alternatives considered**: SSE/WebSocket push — disproportionate for a single-user page with a 3s-tolerance criterion; rejected. Local-only disabling — fails the MCP-triggered case in the criterion; rejected.

## R9: New-vs-updated and cancellation semantics

**Decision**: `runCalendarSync` upserts each fetched event by `graph_event_id`: absent → insert, count **new**; present → compare the full normalized stored representation (event fields + participant set) against the incoming one, and only when something differs rewrite the event row and delete-and-reinsert its participants, counting **updated**; identical → touch nothing, count nothing. After ingesting, cancellation marking (FR-011): select stored events whose span overlaps the synced window; any such event absent from the fetched id set — or fetched with `isCancelled: true` — is marked `is_cancelled = 1` (counted as updated if it wasn't already cancelled). Events outside the window are never touched; nothing is ever deleted (FR-011, FR-014). A previously-cancelled event that reappears in a fetch (e.g. moved back into range, un-cancelled) is refreshed to current state including `is_cancelled = 0` — the moved-event edge case. Each event ingests in its own transaction so a mid-run failure keeps partial progress; the engine returns `status: 'complete' | 'interrupted'` with counts, exactly like `runSync` (`sync.ts:246-273`), and the coordinator maps that to a success/failure history row with error text (FR-013).

**Rationale**: FR-010 defines "updated" as "stored details changed", so unconditional update-counting (what email does for its volatile subset) would report wrong counts here; a full comparison is cheap at this scale and makes US5's "0 new / 1 updated" exact. Bounding cancellation to the overlap set implements the spec's "cancellation detection is bounded by the synced range" edge case verbatim, and the fetched-set-difference approach needs no extra Graph calls.

## R10: Participants — shared address records, four roles, normalized response status

**Decision**: `calendar_event_participants` rows link events to the existing `email_addresses` table through the same find-or-create-by-`lower(value)` logic email uses (`findOrCreateAddressId`, `sync.ts:92-108` — extracted or mirrored for calendar). Roles: `organizer`, `required`, `optional`, `resource` (Graph attendee `type` maps directly; rooms/equipment arrive as `resource` attendees). Response status normalized to `none | accepted | declined | tentative` (Graph `notResponded`/`none` → `none`, `tentativelyAccepted` → `tentative`; the organizer row carries `none`). `display_name` stores the name as seen on that event (empty string when absent — the no-display-name edge case). Unique index on `(event_id, address_id, role)`, index on `address_id`. `isEmailAddressReferenced` (`src/server/services/contact-entries.ts:72-80`) is extended to also check `calendar_event_participants`, so removing/editing a person's address unlinks rather than deletes an address that events still reference.

**Rationale**: Routing through `email_addresses` is what makes FR-015/FR-016 free: case-insensitive person matching is the DB-level `lower(value)` unique index, and adding an address to a person claims the existing row (`contact-entries.ts:92-112`), instantly connecting already-synced events with no re-sync — US3 scenario 2 works by construction. The `resource` role satisfies the clarified resource-mailbox decision; normalizing response values keeps the tool surface small while covering every spec-tested state.

## R11: `list-unlinked-addresses` extension

**Decision**: Extend `listUnlinkedAddresses` (`src/server/services/email/queries.ts:311-341`) with a calendar aggregation: an address qualifies if it is unlinked (`person_id IS NULL`) and appears in mail **or** as a non-`resource` event participant; each row gains `eventCount` (`COUNT(DISTINCT event_id)` over non-resource participant rows, 0 for mail-only addresses) and `messageCount` becomes 0 for calendar-only addresses; `lastMessageAt` becomes nullable (null for calendar-only addresses). Ordering stays `messageCount DESC` with the existing tiebreaks. The display-name pick considers both sources: most recent non-empty name across mail (by `sent_at`) and events (by `start_at`). Addresses seen **only** in the `resource` role never appear (FR-022); an address seen as resource somewhere but person-style elsewhere appears with its non-resource event count.

**Rationale**: Implements FR-022 and US7's exact expected rows (2 msg/3 evt, then 1/0, then 0/1) while changing nothing about how existing mail-only rows sort. Making `lastMessageAt` nullable is the honest shape for calendar-only addresses; the tool's output schema is versioned only by this feature, and agent consumers read `structuredContent` fields additively.

## R12: MCP tool names, shapes, and pagination

**Decision** (resolving the spec's deferred names/pagination/time-representation): tools are `sync-calendar`, `list-events`, `get-event`, `events-for-person`, registered in `src/server/mcp/tools.ts` alongside the existing fifteen (auth is automatic — bearer-gated `/mcp` route, FR-017). `sync-calendar` mirrors `sync-emails` exactly: optional-in-schema `startDate`/`endDate` validated in the handler (missing → "A start date and end date are required"; invalid/inverted → the `computeSyncWindow` error; colliding → "A sync is already running"), source `'mcp'`, no history row on validation failure. `list-events` takes required `startDate`/`endDate` (inclusive local days) and returns all overlapping events ascending by `startAt` with no pagination — the range itself bounds the result, and adding cursors to a bounded query is speculative complexity (recorded as a deliberate deferral). `events-for-person` mirrors `emails-for-person`: `personId`, `limit` (1–200, default 50), opaque keyset `cursor` (base64 `{primary, id}`, `encodeCursor`/`decodeCursor` at `queries.ts:14-35`), ordered newest-first by `startAt` (per the spec assumption), each event carrying the person's matching `addresses: [{ address, role, displayName, responseStatus }]`. `get-event` returns the full FR-008 detail set with `participants: [{ address, displayName, role, responseStatus, person: { id, name } | null }]`. Cancelled events are included and flagged everywhere (`isCancelled`). Categories are stored and returned as a string array (Graph's model, matching `email_messages.categories`); the spec's singular "category" is the array's rendering. `seriesId` (the stored `series_master_id`) is a nullable string on all read tools. Errors use the established `toolError(message)` shape; success responses put data in `structuredContent` with a human summary in `content`.

**Rationale**: Every convention here is lifted from an existing tool so agent ergonomics stay uniform — epoch-ms numbers, keyset cursors, handler-level validation for friendly tool errors, `Person ${id} not found`-style messages. The one naming divergence from `sync-emails` (its `syncedCount`) is deliberately **not** copied: `sync-calendar` returns `newCount`/`updatedCount` matching the run-history vocabulary the spec uses throughout.

## R13: Sync page — calendar section in `SyncPage.vue`, nav renamed to "Sync"

**Decision**: `SyncPage.vue` gains a calendar section mirroring the email section's markup and behavior with calendar-prefixed test ids (`calendar-sync-in-progress`, `calendar-sync-history-empty`, …): two `NDatePicker`s prefilled every visit to today−30/today+30 (rolling window, FR-002 — no history-derived prefill, unlike email), Sync button POSTing `/api/calendar-sync/runs`, result line, `NEmpty` "No syncs yet" empty state, newest-first history list showing when/range/source/status/counts/error (FR-001/003/004/005). Both sections' buttons share the `GET /api/sync/status` polling from R8. The email section's prefill and history are untouched. The nav link and page heading become "Sync" (spec flags this as Tyler-adjustable at acceptance; `tests/component/app-shell.test.ts:37` updates accordingly).

**Rationale**: The page already embodies every needed idiom (validation line, defensive error handling, history rendering, `NEmpty` empty states); duplicating the section with distinct test ids keeps component tests unambiguous. The rolling prefill is deliberately simpler than email's watermark because refresh semantics make re-covering dates safe — confirmed in the brief.
